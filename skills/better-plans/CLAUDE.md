# better-plans: notes for working on the skill

Read `README.md` and `skill/SKILL.md` (and the reference file it routes your area to) first. These are standing facts and traps for anyone changing the skill, its template or its scripts. The skill's users get their rules from `SKILL.md`; this file is for the people building it. Dates are when a fact was last checked.

## Artifact tool behaviour (checked 19 to 21 Oct 2026)

- **Republishing needs the page "viewed".** A session that didn't publish the page itself must do an Artifact `read` of the URL **without** `path`, and then `Read` every line of the saved file it names, or the publish is refused. A refused publish says whether the content matches the live page's; when it does, the refusal counts as viewed and the same publish sent again goes through. A `read` with `path: "index.html"` saves the file without the inline preview but doesn't count as viewed by itself. A `read` without `path` of a small page (under about 50 KB) returns it inline, names no saved file, and counts as viewed. A session that published the page earlier needs none of this.
- **Read chunk size.** Reading a ~190 KB page in 750–900-line chunks often goes over the Read tool's size limit and the chunk has to be re-read. Use 500-line chunks, all as parallel calls in one message.
- **Edit needs only a partial Read.** After any `Read` of a file (even 3 lines), `Edit` works anywhere in it. Don't re-read a page to find a spot; use line numbers from a script.
- **Calls in one message run in order.** `Edit` → `Bash` (script) → Artifact publish can go in one message, and the publish sends the edited file. The flows in `SKILL.md` rely on this.
- **Supporting files persist.** A page published with `files` (`plan.css`, `plan.js`) keeps them when later republished with the page alone. Relative `<link href="plan.css">` / `<script src="plan.js">` is allowed.
- **`files` sources must sit in the session's working directory or scratchpad.** A session in another project can't publish `plan.css` straight from the skill folder. That's why `plan.py files <scratchpad>` and `finish --files <scratchpad>` copy the two files first. The page itself (`file_path`) can be the saved file under `~/.claude/projects/.../tool-results/`.
- **Replacing a published file** (a refresh of `plan.css`) needs the session to have listed the artifact's files (`list` with `scope: "files"`), read that path, or published it; adding a new path needs nothing extra. A publish needs `file_path`; `files` alone is refused.
- **Database writes need no page read.** `ArtifactData` `set` on a new document needs no `if_version`; changing an existing document needs its `version` (so a read). Writes don't create an artifact version.
- **Subagents share the parent session's artifact state**, so a subagent can publish a page the parent published without a full read. For timing tests, make the procedure do the full read anyway so the numbers match a fresh session.
- **A `read` with `path` and `out_dir` saves to `<out_dir>/<path>`**, a path known before the call, so `plan.py outline` can run in the same message. A `read` **without** `path` refuses `out_dir`.
- **Republish test pages with `url`.** Publishing a file this session published, without `url`, after a subagent published a newer version of that artifact, made a separate new artifact instead of updating.
- **Pages that publish themselves.** A page's own `claude.use("artifact").publish(html)` (html form) keeps the supporting files and the stored capabilities, and a later Artifact-tool publish of the stored file recognises its skeleton (no nested `<!doctype>`).
- **Daily publish limit: 200 Artifact publishes per account per day** (429 "daily publish limit for your plan reached (200)", resets at 00:00 UTC), shared by every session on the account. Timing tests need a reset publish as well as each run's own, so plan big test rounds around it.
- **Contract:** don't pass `contract` on a publish unless the person asks; plans on 0.2.85 and 0.2.87 both build from the database.

## Where the time goes

About 95% of an update is model time, so the cost is round trips (3–8 s each) and tokens, not tools. Every flow in `SKILL.md` is shaped to save round trips: most updates are 3 (one message that writes the record and checks the plan's kind, one reply), lookups and future ideas 4, a new plan 5. Keep it that way: a change that adds a message to a flow costs more than almost anything it could save inside one.

## Skill files

- `SKILL.md` is the database plans' core: the routing table with each request's first calls, Headings, record updates, lookup updates, reading for context, and the plan source. `making.md` (new plans: source, `plan.py new`, the seed batch; the template's sections and markup), `ideas.md` (the board's cards and buttons, adding ideas), `selections.md` (Feature Selections on a database plan, accepting straight away), `snapshots.md`, `batches.md`, `light.md`, `older-plans.md` (plans without `plan/_plan`) and `older-selections.md` (their future ideas) are read only when the routing table says. When adding a rule, put it in the file of the request that needs it.
- Every record update's first message also `get`s `plan/_plan` and `statuses/_meta`: that is how a session learns it's on an older plan (no `_plan`), and then it deletes the record it just saved (`if_version` 1) and follows `older-plans.md`; a status-only record stays, since older pages show status records. About 1–2 s per update for the two gets.
- The routing table gives each request's **first calls**, so the reference `Read` rides in the same message. Without that, test runs read the reference file in a message of its own (+1 round trip).
- The frontmatter `description` is how the skill is chosen. Keep "load ArtifactData with the skill when deferred" in it: a run that loads the deferred tool in a message of its own takes a round trip more.
- Feature Selections on an older plan is three messages: (1) `read` + `features` and `statuses` lists; (2) parallel full Reads + `apply_selections.py report`; (3) Edits + Write plans file + `apply` + publish + database batch, in that order. `report` prints each EDIT card's line range (and a planned feature's overview rows), a `BOARD` line, a `FORMAT` line for single-file pages, and `REFERENCE` lines from a trial `apply` with stand-in steps (`preview_refs`), so taken-out mentions can be reworded before `apply`. `apply --files` copies `plan.css`/`plan.js` like `finish --files`. The batch clears edits in the same message as the publish: if `apply` fails, the publish fails too (no `--out` file) and the edit texts are still in the report and the local `features` folder, so a rerun is consistent.
- **Batches** (`batches.md`): optional, opt-in only. They need no script or `plan.js` change: badges are `<kbd>` in step names (on the inline allowlist; side batches with a dashed `<small>` badge were dropped in 1.3.0 after a user read one as part of the batches around it), the badge CSS is the plan's own `_plan.styles` (no record field sets it, so an `ArtifactData` `update` of `_plan` plus a snapshot, since the styles live only in the published page's head), and the rules a batch session follows are the plan's Running a Batch subsection, so each plan can change them. `plan.py new` with badged names, `## Styles` and a Batches table builds cleanly (the table's step numbers become `{{S:…}}` tokens).
- Accepting an idea straight away on an older plan rides on the same three messages: in message 3, Edit in the card, `Write` `<scratchpad>/db/features/<id>.json` (`{"decision": "accept"}`) so `apply` sees the choice, and add a `set` of it to the batch.

## New plans

- `plan.py new SOURCE --files <scratchpad>` (in `plan.py`, using `htmlplan.parse_source`/`build_page` and `dbplan.convert`) writes the first snapshot page and the entries as `<files>/seed/_plan.json` and `_seed.json`; the session publishes with `files` and the five capabilities, then sends one `batch` of three writes (`_plan`, `_seed`, `statuses/_meta`). New text is checked against the allowlist and refused with the reason.
- The source holds only what Claude decides: `# Title` + summary, `## Section: Name {#id}`, `## Phase: Name` + optional intro, `### Step: Name [status] {#id}` + body, `## Idea: Name {#id}` + sentence + details, `## Styles`. Everything derivable (header, dates, version, overview, rowspans, numbering, statuses, phase pills, progress, card wrappers, back links, board, template head) is the script's. `{#id}` on steps and phases sets their doc ids (`s-<id>`, `p-<id>`); `source_ids` in `dbplan.py` renames convert's name-based ids and the step tokens that point at them.
- The format was chosen by measurement over a JSON spec (+18% tokens, and HTML in JSON strings is escaped twice once it's inside a Write call) and custom tags (+5%). Markdown-style headings are what models write most reliably; every test run wrote a valid source first time. Writing the source instead of the page cut the tokens Claude writes by about 65% and the time by about 40%.
- The output must stay byte-for-byte what the template and `making.md` describe, since `outline`, `finish`, `apply_selections.py` and `plan.js` parse it. Rerun a round trip (pages turned back into sources and rebuilt, then compared) after any change to `build_page`.
- Lenient on purpose: step and phase numbers in headings are ignored (`## Phase 2: X`), statuses accept labels (`[In progress]`, `[not started]`), plain-text paragraphs become `<p>`, a bare `<table>` gets `.table-wrap` and `class="table"`, a bare `<svg>` the `.diagram` div, and in extra sections runs of text, `<h4>` and lists are grouped into `.prose` divs. Lines inside `<pre>` are never read as headings or re-indented. Strict where a guess would be wrong: unknown headings, text under a label heading such as `## Future Ideas`, empty steps or phases, unclosed tags, duplicate ids and a missing summary stop it with the source line, and it writes nothing, so the publish in the same message fails too.
- `--version` and `--created` let a rebuilt plan keep its version and Created date, but a source can't hold planned features (F phases) yet.
- The `making.md` read is still a round trip of its own after the skill loads. Putting the source format in `SKILL.md` would save it (~5 s) but adds ~2k tokens to every request; not done.
- **Auto mode and scripts in the scratchpad:** auto mode's safety check once blocked `plan.py new` run from a copy of the skill in a session's scratchpad ("Code from External"). Real sessions run the script from the skills folder, so the flow needs no change, but timing tests that run a skill copy from a scratchpad can be blocked: count such a run as blocked, never route around it.

## Page format

- Plans are split: the page holds `template.html`'s skeleton (title, fonts, `<link rel="stylesheet" href="plan.css">`, content between the PLAN CONTENT markers, `<script src="plan.js">`), and the look and behaviour live in `skill/plan.css` and `skill/plan.js`, published beside each plan. There's no build step.
- A plan's own `<style>` blocks (marked `/* plan-specific */`) go straight after the `plan.css` link. `apply_selections.wrap()` keeps them when it rewraps a page (`plan_styles()` skips the template's block, recognised by its `better-plans template` comment, and the Artifact runtime's `<head>` style in saved files).
- Older single-file plans move to the split format the next time `plan.py finish` or `apply_selections.py apply` writes them, with their content unchanged.
- `plan.py outline` says which format a page is in, and `finish` prints every change it made. Keep both working on both formats.

## Database statuses

- A status record is one new document in the plan's `statuses` collection, `{"steps": {"2.3": "done"}, "at": ISO UTC time, "date": local YYYY-MM-DD}`, written by `plan.py` and saved with `ArtifactData` `set` + `file_path` in the same message (calls run in order, so the Bash output file exists when the `set` runs). A new document needs no `if_version`, so no read first. The model can't know the time without a tool call, which is why the body comes from a file.
- `statuses/_meta` (`{"statuses": 1}`) marks a plan whose published `plan.js` shows records and whose capabilities carry the `statuses` rule.
- Folding back on an older plan: `finish --db` / `apply_selections --db` apply records newer than the page's `<dl class="meta" data-baked="...">` time, then stamp the newest record's `at` there. `plan.js` and the scripts ignore records at or before the stamp, so deletes are only cleanup: records are deleted on the full update **after** the one that folded them in (`outline` names them), never in the same message as the publish that folds them, since a refused publish would lose them.
- Store facts: step numbers with dots work as keys inside `steps`. `list` with `out_dir` writes only the document body to each file (the `version` is in the tool result). Avoid `:` in doc ids: `out_dir` uses the id as a Windows file name. With rules `{"path": "statuses", "read": "view", "write": "admin"}`, `list` at `as_level: "view"` returns the records and a `set` at `as_level: "interact"` is refused as not found.
- Models don't make random ids: five runs asked for "10 random characters" wrote `r-k7m2q9x4v1`, `r-k7m2q9x4tz`, `r-k7m2q9x4b1` and so on. A clash is safe (a `set` on an existing document is refused and the session retries), but the id also carries the date, step and status (`r-20261019-2.3-done-qkxw`) to make one unlikely.

## Database plans

`skill/dbplan.py` (model, replay, builder, fold, convert, records), `skill/plan.py` (one CLI for both kinds of plan; `outline PAGE` and `finish` hand over to `htmlplan.py`), `skill/plan.js`, and the skill files. A plan is a database plan when its `plan` collection has `_plan`; `statuses/_meta` alone isn't enough to tell.

- **Layout.** One collection, `plan`: `_plan` `{kind: "plan", title, summary, version, created, updated, bakedAt, styles, snapshotAt}`; core phase `p-<slug>` `{kind: "phase", name, intro, sort}`; planned feature `p-<feature id>` `{kind: "phase", feature, name, short, desc, sort}`; step `s-<slug>` `{kind: "step", phase, name, body, status, sort}`; section `x-<html id>` `{kind: "section", id, name, body, sort}`; idea `i-<feature id>` `{kind: "idea", feature, name, sentence, details, sort}`. Numbers are never stored (sort keys spaced 1000, midpoints for inserts). An idea whose feature id is also a planned feature is hidden: the plan replaced it.
- **Seeds.** A new or converted plan stores its entries in one document, `_seed` `{entries: {doc id: entry}}` (`_seed2` … past ~200 KB; a document holds 256 KiB). An entry document of its own wins over the seed's entry of the same id, and `{deleted: true}` hides one. So creating a plan is one `batch` of three writes, and a `list` of `plan` prints a few lines instead of one per entry.
- **Every update is one record** in `statuses`, never an entry write: `steps` and `notes` by number, plus `set`, `rename`, `swaps`, `takeout`, `add`, `moves`, `order` (full spec: `Model.replay`'s docstring in `dbplan.py`). Targets are step numbers, phase or feature numbers, `idea:<id>`, `section:<id>`, `plan`, a doc id, or a name exactly as shown (a unique match only). Numbers mean the plan as it stood just before the record, so a session that never listed the plan can still name things: `plan.py record` needs no list. The lookup commands (`edit`, `add --db`, `move`) write the same records, by doc id, after checking the text or place exists. Only a snapshot writes entries. Records need no `if_version`, and structural records replay in order, so later by-number records name the right steps.
- **Replay** (`Model.replay`; `buildModel` in `plan.js` does the same, checked by the parity test): records newer than `_plan.bakedAt` in time order. Each record's targets resolve against the numbers before it; then set, rename, swaps, takeout, add, moves, order; renumber; then statuses and notes. A record with a `checkpoint` (early records, and the fold record) resets the plan: its `entries` replace entries (null removes), statuses and notes reset by id, and everything before the last checkpoint is skipped as already in the entries. A swap whose old words aren't there changes nothing, and `outline` lists it under "changes that changed nothing", as it does steps or targets that don't resolve. An add whose doc id is taken by an entry with the same name is skipped (a resend); with another name it gets `-2`. Race not handled: a by-number record another session writes just after an insert it didn't see resolves against the new numbers.
- **Step and feature numbers in text** are tokens, `{{S:<step doc id>}}` and `{{F:<feature id>}}`, shown as the current number (`?` or `F?` once gone). `tokenize_html` (`tokenizeHtml` in `plan.js`, same rules) runs on `convert` and on every record's text at replay, against the numbers when the record was written. Fn.m and Fn always, when that step or feature exists; core n.m only when it's a step and reads as a reference: not inside `<code>`, `<pre>`, `<kbd>` or `<svg>`; not after a letter, `.`, `$`, `#`, `/`, `-` or a version-ish word (version, v, python, about, over, than …); not before a unit (days, s, ms, %, x, MB, tokens …), another `.digit` or an arrow. Known false positives: "F5 key" follows feature 5; example numbers ("a step number like 2.3"), version numbers ("bump the minor number (1.1, 1.2)"), a duration range ("2.5–3 minutes"), and another plan's numbering ("its phase 3.2"). Possible rules, not built: skip a number followed by a dash and a plain integer, and one after the word "phase". A change needs both `tokenize_html` and `tokenizeHtml` and the parity test.
- **Numbers in an add's own new parts:** the text of the parts an `add` makes (new steps, phases, features, sections, ideas) is tokenized again after the record, against the numbers before it plus, for numbers the plan didn't have yet, the numbers after it (`fresh` in `apply_record`/`add_part`, `applyRecord`/`addPart`). So a new feature naming its own steps ("passed in F1.1") follows them; numbers that existed keep their before-the-record meaning, as targets do. Published plans pick it up when their `plan.js` is next refreshed.
- **Allowlist** (`cleanFragment` in `plan.js`; `check_html` in `dbplan.py` with the same lists): inline fields `a b br code em i kbd s small strong sub sup span`; bodies add block, table and svg tags; classes `prose note note-label diagram table-wrap table d-*`; `href` only `#…` or `https://…`; `target` only `_blank` and `rel` only noopener/noreferrer/nofollow; no `style`, event attributes, `img`, `figure` or forms. `record`, `add`, `edit` and `new` refuse text the page wouldn't show, saying why; `convert` and `snapshot` list it. A plan with an image in it can't be converted without losing the image; it stays an older plan.
- **Converting** (`plan.py convert PAGE OUTDIR`) refuses pages not built from the template. A note between a step's `.prose` div and its back link moves to the end of the details (inside `.prose`, so it gains the 0.75rem gap `.prose > * + *` gives), with a warning. Ideas mixed between planned features on the board come out after them, with a warning; the page groups them the same way either way. Older pages' "Future Features" become "Future Ideas", as `finish` does. `convert` sets `_plan.snapshotAt`; without it the line says "No snapshot yet".
- **How to convert a plan:** download with `read` + `path`; list `statuses` and `features`; fold pending records (`finish --db`) and check `features/_order` matches the page (it's ignored on a database plan); `convert`; review every token in context (a small script printing ~40 characters either side of each token is enough) and turn false positives back into plain numbers in `_seed.json` before seeding; try it on a private copy first (published with `files` and the five capabilities, seeded with one batch: `_plan`, `_seed`, `statuses/_meta`, plus copies of the `features` documents); then the real plan: `snapshot` of the conversion with the plan's own `statuses` and `features`, a full read, `list` with `scope: "files"`, publish to its `url`, one batch (`_plan`, `_seed`, and `_meta` only when missing). The quickest correctness check is the page's own snapshot line: "up to date" means the page built from the database exactly matches the published snapshot.
- **Version and dates:** `_plan.version` plus 0.1 per record, or the next major for `major: true` (which `record` sets for add, move, takeout and order). A fold record (`fold: true`) counts for neither. Last updated is the newest record's date.
- **Rules and capabilities:** `{"path": "plan", "read": "view", "write": "admin"}` beside `features` and `statuses`; a new plan declares those three, `user` and `artifact` (for Save Snapshot).
- **Drag on a database plan** saves one record `{order: [feature ids], major: true}`, and the page replays it at once; statuses stay with their steps. `features/_order` is ignored on database plans.
- **Status order:** `number()` (both sides) sorts core phases and planned features by phase status (`STATUS_RANK`: done 0, progress/blocked 1, todo 2, skipped 3; stable within a group) and numbers them in that order, so a status record can renumber phases. `m.storedPhases`/`stored_phases` keep the sort-key order, which `add` (after phase N) and `move` use. It's gated on `_plan.statusOrder`: records written before it target by number against the unsorted order, and replaying them sorted misresolves them. A snapshot (page fold, `plan.py snapshot --fold`) bakes those records into entries and sets `statusOrder: true`; `new` sets it from the start. `scen.py` 17–21 cover it.
- **Settling (`stay`):** with the sort alone, a phase's place inside its group comes from its sort key, so one that changed group jumped to wherever its key fell (an unskipped feature went back to its pre-skip place above features added since; a finished one landed among older done ones). `plan.py` now marks every record that sets statuses `stay: true`, and replaying it (`settle`, both sides) gives each phase whose group changed a new sort key: the end of its new group going up, the top going down. The stored order then matches what's shown, and a snapshot bakes the keys. Records without `stay` (written before 25 Oct 2026, or by older copies) keep the old meaning, since later by-number records were written against the numbers it gave. Published plans pick it up when their `plan.js` is refreshed; until then the page and `outline` can number a regrouped feature differently.
- **Overview phase folding:** every phase with steps can fold (`can-fold`). Finished (done or skipped) phases fold by default; a click is kept in `foldChoice` with the finished state it was made under and dropped when that changes, so a phase still folds itself on finishing.
- **Group folding** (`regroup()`, end of `refold()`): finished core phases (all of them, `GROUP_MIN_CORE`+) and the leading done planned features (`GROUP_MIN_FUTURE`+) fold into one DOM-only group row each, kept in `groupChoice`; snapshots and parity never see them. Opening the features group glides to the next one or two phases; closing it (from the `group-end` row) glides back. `y0` is read before the rows change, since scroll anchoring shifts the page.
- **Back to next step:** the corner button glides to the overview's first row that isn't done or skipped (`nextRow()`, read at the click; `.split` and `.is-reset` tbodies left out), a third of the way down the window, or to the top when every row is finished.
- **Publishing over a large live page** needs it read in full first (a 5,000-line plan is about 155k tokens; a subagent can do the read and the publish to keep it out of the main session). A refused identical resend goes through on the second try.
- **Snapshots and the fold.** The page's HTML is only a snapshot. The owner's **Save Snapshot** line, under the summary ("Snapshot <date> · up to date" or "· the plan has changed since"), folds and republishes from the page with `claude.use("artifact").publish(html)`. The page's database API has no batch or transactions, so the fold goes: (1) one **fold record**, a checkpoint holding every changed entry (`entries`, `meta` with title and summary, `fold: true`), which shows the same plan at once; (2) each changed entry `set` (seeded or not), removed ones deleted or tombstoned; (3) `_plan.update({version, updated, bakedAt: the fold record's time, snapshotAt, title, summary})`; (4) deleting every record at or before that time; (5) the publish. Stopped at any point, the page shows the same plan (`scen.py` checks each stage). The published page is the Artifact skeleton (`SKELETON` in `plan.js`, copied from a saved file) + a line break + the template's head + the cleaned built content + `\n</body></html>`. `plan.py snapshot --fold` does the same from Claude's side and prints the writes in order. A plan's own `styles` go only in the snapshot's head, and only without `url(`, `@import` or `</style`.
- **Automatic snapshot:** `snapshotBar()` calls `autoSnapshot()`, which runs `saveSnapshot(true)` once per page load when `snapshotDue()` says so: the plan differs from the snapshot **and** `_plan.snapshotAt` is over a day old (or missing) **or** more than 30 update records are pending (`pendingRecords`, fold records not counted). It waits for both collections to come from the store, not the cache (`hub.live`, from `snap.metadata.fromCache`; a stale cached `statuses` would fold with a `bakedAt` that hides records it never saw), then 1.5–3 s (random part for two tabs), and puts itself off while a card is dragged or an edit box has the focus. Only the owner and editors get there (the bar needs `canEdit`). Two tabs: `claim()` takes a 90 s lease on `statuses/_snapshot` (`acquire`, holder = a per-load tab id, so the same tab can retry); busy means the auto save skips quietly and the button says another tab is saving. Without `acquire` (older runtimes) or if it fails, the save goes ahead and the fold-record check (`foldUnderway`, one from the last 2 min) and the publish's `conflict` are the guard. The save rebuilds the model from `hub.plan`/`hub.statuses` after the lease. `_plan.snapshotAuto` (true from the automatic save, false from the button; `plan.py snapshot --fold` drops it) makes the line read "Snapshot saved automatically <date>, <time>"; every view reloads after the page's publish, so the flag is how the line knows. The runtime's guidance says to publish only after a viewer acts; on-load publishes worked with no prompt (desktop app and Chrome) when this was built, so watch for that changing.
- **"Changed since"** compares the built content with the page's own copy, both trimmed: the page's copy starts with one more line break, which made every load swap once and the line always say "changed".
- **Store limits:** a document ≤256 KiB, a batch ≤50 writes and 1 MiB, 25,000 documents per artifact, 64 subscriptions per view, queries scan the collection. A fold record over 250 KB is refused ("fold in two goes"). The outline mentions the automatic snapshot past 30 records (`SNAPSHOT_HINT`, the same threshold as `AUTO_RECORDS` in `plan.js`): that many pending means no editor has opened the page since.
- **The page (`plan.js`)** shows the snapshot, then builds from `plan` + `statuses` once both arrive and swaps only when the built content differs. It rebuilds on every change, keeps open cards, open idea details and the scroll position, and waits while a card is dragged or an edit box has focus. Without `_plan` it behaves as an older plan (status records over the HTML, `_order` drags).
- **Which plans have a feature:** a plan runs the `plan.js` it was last published with. A change to `plan.js` reaches a published plan only when its look is refreshed (Artifact `read` without `path` and `Read` every line, then publish the saved file to its `url` with `files` mapping `plan.js` from a scratchpad copy). Ask before refreshing someone's plans.

## Tests

`python -I tests/run_all.py` runs all four suites against `skill/` and exits 1 on a failure: `scen.py`, `parity.js` on `scen.py`'s cases, `autosnap.js` and `idea_target.py`. `parity.js` and `autosnap.js` need Node.js. Rerun it after any change to either model. Each script also runs alone, defaulting to `../skill` and the `sample-db` fixture (a made-up plan, "Larder Build Plan", with four phases, eight planned features, eight sections and step references across them), or takes other paths: `scen.py [SKILLDIR DBDIR]`, `parity.js [PLANJS] CASES`, `autosnap.js [PLANJS DBDIR]` (run it on an older `plan.js` from `git show` to see what a change fixed).

- **`scen.py`** (every record kind, seeds and overlay, the tokenizer, the allowlist, checkpoints, edit/add/move by id, a fold stopped at each stage, an add naming its own steps then a drag, status order) dumps its cases with `DUMP=<file>`; **`parity.js`** runs `plan.js`'s `buildModel`, `buildContent`, `foldPlan` and `tokenizeHtml` in node (cleaning and `textOf` stubbed) on them and compares. Its scenarios name the fixture's steps and features by number and doc id, so a change to `sample-db` needs the matching change in `scen.py`.
- **`autosnap.js`** runs the real `plan.js` per "tab" against a fake store, user and publish (up to date, recent, a day old, 30 vs 31 records, viewer, two tabs with and without the lease, cache first, lease held elsewhere, the line after the reload).
- **`idea_target.py`** checks `idea:<id>` targets resolve both ways, in `dbplan.py` and `plan.js`.
- **`realcmp.py OLDSKILL NEWSKILL DBDIR…`** builds listed plans (database folders as `ArtifactData` `list` with `out_dir` writes them) with both skills and prints differing lines. Use it on copies of real plans before a change to the model ships.
- **Script tests on real pages:** download copies with Artifact `read` + `path: "index.html"` (no full read needed, never publish them), run `plan.py finish` on copies and diff: only the expected lines may change.
- **Look tests:** serve before/after pages from a scratch folder with `python -m http.server <port> --bind 127.0.0.1`, open them in the built-in browser with `preview_start` (`url`), and compare computed styles and bounding boxes of every element in two same-width iframes, light and dark, 1280 and 375 px. `resize_window` with `colorScheme` works on a localhost server. The browser pane runs hidden, so `requestAnimationFrame` never fires there: wait with `setTimeout`, and start long scripts without awaiting them, then poll.
- **Real pages in the built-in browser:** Artifact pages render in a cross-origin iframe (`*.frame.claudeusercontent.com`): `find`, `get_page_text` and `javascript_tool` can't see inside, so check with screenshots and `zoom`, and check writes with `ArtifactData` `list`. While the pane is hidden, `left_click_drag` on a drag handle works; clicking a handle doesn't focus it, so the arrow keys move a card only after Tab. Bring the tab to the front with `tabs_select` before driving it.
- **The page's database code locally:** put a small stand-in before `plan.js` that defines `window.claude.use('db')` returning collections whose `onSnapshot` delivers fixed documents (and `use('user')` with `canEdit`). Compare old and new `plan.js` under the **same** stand-in (empty database, `use('db')` resolving null, and no `window.claude` at all): with a stand-in on only one side, the owner buttons appear on that side and every card differs.
- **Sharing:** checked with `ArtifactData` `as_level`, a viewer the plan is shared with can read the live plan (`list` at `view` returns the documents) and nobody but the owner and editors can write (`set` at `interact` is refused). Not yet tested with real accounts: a signed-out visitor, a shared viewer and a stranger with a public link. Expected: signed out sees the last snapshot; signed-in viewers see the live plan with no Save Snapshot line and no idea buttons (`canEdit` false). To test, use a private test copy with a status record the snapshot doesn't have (a viewer who sees it is reading the database). Never share a real plan for a test.
- **Python can't read the desktop app's notes folder** (`%APPDATA%\Roaming\Claude`) from Bash on Windows; see Light plans. Copy tools into the scratchpad first.

## Timing tests

- **Measure from transcripts.** Run each variant as a subagent with the same request, then read its transcript at `~/.claude/projects/<project>/<session id>/subagents/agent-<id>.jsonl`: total time from first to last timestamp, round trips (distinct assistant `message.id`s), and context added (cache read + creation on the last call minus the first). `python tests/measure.py LABEL=<transcript> …` prints all three plus the model, the model time before each round trip and every tool call. The Agent tool's `output_file` can come out empty: use the `subagents/` transcript.
- **Keep test batches small.** Each subagent starts with tens of thousands of tokens of fresh context. Round trips and context added come out identical across repeat runs of the same request on the same skill, so measure those with one run per request kind; run three only for the kinds whose time is the result. API speed swings within the hour, so more repeats don't remove that noise; a same-window control run next to each timed run does. Pilot with one run, then start the batch.
- **Models:** timing runs use the model and effort the skill's real sessions use. Runs that only check the page came out right can use a smaller model.
- **Test pages:** make fresh private copies of a plan for a test, and delete them afterwards. Subagents have no desktop task list or next-step box; a real desktop session adds about 7–12 s per turn on top.
- **Nested `CLAUDE.md` in timing tests:** a subagent that Reads a skill copy inside its working folder gets every `CLAUDE.md` on that path attached (this file is ~10k tokens). The installed skill under `~/.claude/skills` doesn't trigger it. Run test copies from outside the working folder, or subtract it.
- **Handing updates to a smaller model doesn't pay.** A Sonnet or Haiku subagent doing an update for an Opus session was slower end to end (73 s and 99 s against 40 s for the session itself on the same request): the handoff costs 9–10 s fixed, a smaller model's round trip is only 2–3 s faster, and fresh subagents explore (reading the skill again, running `outline` several times). A handoff only breaks even past about 6 parent round trips, and every flow is 3–4. Its one gain is ~10k less context in the parent. Revisit only if the model gap per round trip grows a lot.

## Light plans

`skill/light.md` is the format and rules; `skill/session_resume.py` the SessionStart hook, added by `install.py` through `~/.claude/tools/better-plans` (no matcher, `python -I`).

- **Session key:** `CLAUDE_CODE_HOST_SESSION_ID` holds the desktop app's `local_…` id, which stays the same across `/clear`. The CLI id (`CLAUDE_CODE_SESSION_ID`, and `session_id` in hook input) changes on `/clear`. Never key by project folder: several sessions share one.
- **The desktop app is a packaged (MSIX) Windows app.** Its `%APPDATA%\Claude` is really `%LOCALAPPDATA%\Packages\Claude_*\LocalCache\Roaming\Claude`. Claude's tools (Read, Write, Edit, Bash's `ls`) see the Roaming path; Python doesn't. The hook globs `Packages\Claude_*\...` for it.
- **The app's `/clear` reports `source=startup`, not `clear`.** It starts a fresh CLI process (new transcript, new CLI id, same `local_…` id). The hook restores on `startup` too. That's safe: a new session's `local_…` id has no plan yet, and reopening a session reports `resume` (context kept, skipped). Hand tests with fake `source=clear` stdin can't catch this; test with a real `/clear`.
- **Outside the desktop app** (no `CLAUDE_CODE_HOST_SESSION_ID` and no notes folder) the hook returns at once and writes nothing.
- **Hook log:** one line per session start in `~/.claude/better-plans-session-resume.log` (source, host id, CLI id, plan found, files removed; last 500 lines). Use it to check the hook fired and to count clears and compacts.
- **Cleanup** deletes only `*/session-plan.md` files older than 14 days in the notes folder, never other files, and leaves the folders.
- macOS and Linux: untested. The desktop app's notes folder there isn't known to the hook, so light plans aren't restored.

## Shared palette

`plan.css`'s colour and font tokens are shared with artifact-style's `house.css` (`skills/artifact-style/skill/` in this repo), the look of every other Artifact page. Change both in the same edit, then run `python -I skills/artifact-style/tests/check_sync.py` from the repo's root, which fails when they differ. The `plan-css-sync` job in the `secret-scan` workflow runs it on every push.
