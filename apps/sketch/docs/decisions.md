# Sketch design decisions

Why Sketch is built the way it is, phase by phase. Read the section for the part you're changing before changing it.

## Decisions for Phase 1

- **Stack:** Tauri 2 + TypeScript + Vite + Preact (JSX via tsconfig `jsx: react-jsx`, `jsxImportSource: preact`; no Vite preset needed). Hand-write the scaffold (no interactive `create-tauri-app`). Vite dev server binds `127.0.0.1:1420`, strictPort.
- **Runs in a plain browser too.** All Tauri calls go through `src/platform/` with a browser fallback (file input, downloads, `navigator.clipboard`, `confirm`), so the drawing code can be tested in the built-in browser pane on the Vite server.
- **Layout:** see the README. `tests/` holds Vitest tests of pure logic only (node environment).
- **Document model:** each pixel layer is one `OffscreenCanvas` of document size. Undo is tile-based: `PixelEdit.touch(rect)` snapshots each 256 px tile the first time it's touched (copied with `drawImage` into a small canvas, no GPU readback), `finish()` snapshots "after" tiles and returns a command. Restore with `clearRect` then `drawImage` (never `globalCompositeOperation = 'copy'`). Canvas resizes and paste-into-blank are `DocStateCommand`s that swap whole canvases. `CompositeCommand` groups steps (paste plus canvas growth is one undo step). Commands capture their document; `History` holds done/undone stacks, a 1 GB memory cap that drops the oldest steps, an absolute position with a saved position for the dirty flag, and a clickable history list.
- **Doc fill:** new pictures are 1280 × 720 with a white bottom layer; `doc.fill` is the colour used when the canvas grows. Pasting into an untouched new picture makes the document exactly the image. For pasted and opened images, `fillFor` makes the fill white unless the image has see-through pixels, in which case it's `null` so growing keeps transparency.
- **Paste:** the `paste` event first (image items, then `files`), then on Tauri a Rust command reading Explorer file paths from the clipboard (`clipboard-win` `FileList`), then image URLs or `data:` URLs from text or HTML (`fetch_url` Rust command with `ureq` 2). Pasted images float with a dashed outline: drag or arrow keys to move, Enter or click outside to place, Esc cancels (and undoes the canvas growth). Ctrl+Z while floating cancels the float.
- **Copy:** Ctrl+C copies the floating paste or else the whole picture; Ctrl+Shift+C always copies the merged picture. On Tauri, raw RGBA goes to a Rust `copy_image` command using `arboard`; check afterwards that the clipboard holds a PNG format so transparency survives (add `clipboard-win` PNG writing if not).
- **Files:** Rust `read_file` returns raw bytes (`tauri::ipc::Response`); `write_file` takes a raw body with a percent-encoded `path` header and writes to a temp file then renames. Decoding uses `createImageBitmap`. Encoding happens in a Web Worker (`OffscreenCanvas.convertToBlob` for PNG, JPEG, WebP; a hand-written 24-bit BMP encoder), not in Rust as the plan first said; JPEG and BMP flatten onto white. `.sktch` is a zip (`fflate`) with `document.json` plus one PNG per layer. Unsaved-changes, keep-layers-or-flatten and Save As (format, quality slider, live size estimate) are in-app Preact modals, not native dialogs. Native open and save pickers come from `tauri-plugin-dialog`.
- **Drag and drop:** Tauri's `onDragDropEvent` (positions are physical pixels). A drop on the picture adds the image as a new layer; a drop on the grey area opens it.
- **Viewport:** screen = doc × zoom + pan, zoom 2% to 6400%, Ctrl+wheel and pinch zoom around the cursor, wheel pans, Space or middle drag pans, Ctrl+0 fits, Ctrl+1 is 100%. Smoothing only below 100%; pixel grid from 800%. Paint-style resize handles on the right, bottom and corner edges.
- **Startup:** the window starts hidden (`visible: false`) and is shown after the first frame. An `app_ready` command writes a file named by the `SKETCH_STARTUP_PROBE` env var and exits; `scripts/startup-check.mjs` times spawn to that file (median of 5, budget 1000 ms, `SKETCH_STARTUP_BUDGET_MS` overrides). A size check fails over 15 MB. CI on `windows-latest`.
- **Release profile:** `lto = true`, `codegen-units = 1`, `opt-level = "s"`, `panic = "abort"`, `strip = true`. Library crate type `rlib` only.
- A basic round brush (primary on left click, secondary on right) is included in Phase 1 only to exercise undo; step 3.1 replaces it.

## Decisions for Phase 2

- **One command list** (`src/app/commandList.ts`) feeds the menus, shortcuts, palette and shortcuts sheet. Commands a later step builds are listed with `planned` and show greyed out with their step. Ctrl+V stays with the browser's paste event; menu Paste reads the clipboard through Rust (`read_clipboard_image`, `read_clipboard_text`).
- **Keys** are strings like `Ctrl+Shift+S`, read from `e.code` (`src/app/keys.ts`), so `?` is `Shift+/`. User changes are stored as overrides by command id; a key given to one command is taken off the command that had it.
- **Tools** (`src/tools/registry.ts`) declare their options; the options bar builds itself from them. Unbuilt tools are selectable, and drawing with one shows a toast naming its step. Per-tool settings, the slot's last tool, key overrides, recent colours and the panel state are saved in `localStorage` through `src/app/prefs.ts` (debounced, flushed on close).
- **Brush opacity** is applied per stroke: a see-through stroke draws solid on its own canvas (`app.liveStroke`, shown by the renderer) and is blended onto the layer when it ends. Type, smoothing and pressure wait for step 3.1.
- **Colours** are hex strings, `#rrggbbaa` when see-through. The colour popover keeps hue in its own state so greys don't lose it; the screen eyedropper uses WebView2's `EyeDropper`.
- **Icons** come from `lucide-preact`, mapped by name in `src/ui/icons.tsx`. Tooltips are one shared component reading `data-tip` and `data-keys`.

## Decisions for Phase 3

- **Object layers.** `Layer` is `PixelLayer | ObjectLayer` (`src/engine/document.ts`). An object layer's `objects` array is never changed in place: every edit makes a new array, so `ObjectsCommand` and `DocStateCommand` keep the old one for undo. Text objects, their layout, drawing and how they follow crop, resize, rotate and flip are in `src/engine/objects.ts`. Pixel tools draw on `doc.paintLayer` (the current layer if it holds pixels, else the nearest pixel layer below). New text goes into the current object layer, or the one just above the current layer, or a new layer called Text. `.sktch` files are version 2 only when they hold an object layer, so pictures without text still open in older builds.
- **Whole-picture changes** (crop, canvas size, resize, rotate, flip, trim) all go through `changeDocument` in `src/engine/commands.ts`, which makes one `DocStateCommand` covering every layer's pixels and objects. Canvas Size anchors the picture in the middle by default; new space on the bottom layer gets `doc.fill`. Resize halves in steps before the last scale; Pixel Art uses nearest pixel.
- **Strokes** (`src/tools/stroke.ts`): see-through strokes, the highlighter and pen-pressure opacity draw on a live canvas blended at the end (`LiveStroke.blend`; the highlighter multiplies). Marker: a flat nib at 45°, 75% strength. Highlighter: a tall nib, 45%, multiply. Pencil: Bresenham squares, no anti-aliasing. Eraser to transparent draws `destination-out` straight on the layer. Smoothing follows the pointer at 45% and draws curves through the midpoints. Pressure-opacity pieces have flat ends so they don't overlap into dots.
- **Fill** (`src/engine/flood.ts`, run in `src/tools/flood.worker.ts` through `floodClient.ts`, one job at a time): colours compared premultiplied, distance 0 to 1. Pixels up to 2 px outside the area that are a blend of the area's colour and a line's colour get the area's share swapped for the fill colour (exact when sampling the current layer, partial strength when sampling the whole picture), so fills meet anti-aliased lines with no fringe. Pixels of the area's own colour beyond a thin line are skipped, so fills never leak through it. The magic wand uses the same area search.
- **Selection** (`src/tools/selection.ts`, box maths in `src/tools/box.ts`): pixels stay in the layer until moved, resized or turned; then they're lifted (leaving a see-through hole, as the plan's Delete does) with one `PixelEdit` kept open until the selection is placed. Esc reverts that edit. A pasted picture is a selection with `pasted` set, so it gets the same handles. Changing to a tool outside the Select slot places it. Rotate and flip in the Image menu act on the selection when there is one.
- **Crop tool** (`src/tools/crop.ts`): the box resets when the picture's size changes. The options bar's Crop button is an `action` option that runs a command from the command list.
- **Text editing** (`src/ui/TextEditor.tsx`): the picture draws the text (outline and box included); a textarea over it holds the caret, with see-through letters laid out the same way (baseline from `fontBoundingBoxAscent`, the CSS line-box rule). Click on the picture, Esc, Ctrl+Enter or changing tools finishes; the dashed frame drags the text.
- **Colour picker** sets the colour and stays on the picker (Paint switches back; Alt+click covers quick picks). Alt+click picks with any tool that has the colour chips.
- **Listeners instead of imports**: tools react to tool changes, option changes and colour changes through `onToolChange`, `onOptionChange` (`src/app/tools.ts`) and `colorSignal` (`src/app/store.ts`), which keeps `app/` from importing `tools/`.

## Decisions for Phase 4

- **Shapes and lines are objects** (`src/engine/shapes.ts`) in the same object layers as text, and new ones go in the same place (`objectLayerForNew` in `document.ts`); a new layer is called Shapes. A shape is a box turned round its centre, like a selection (`Box` in `src/tools/box.ts`), so the selection's resize and turn maths work on it unchanged. Polygon and star corners are stretched to fill the box exactly, so the handles sit on the shape. A line is two ends plus `bend`, how far its middle is pulled sideways; it's drawn as a quadratic curve, and `bend` survives moving either end. A filled arrowhead's line stops short of the tip so its width doesn't stick out. See-through objects are drawn solid on a spare canvas and blended (`drawFaded`), so where the fill, outline and heads overlap isn't darker.
- **Picking** (`src/tools/shapes.ts`): the Shapes, Lines and Select tools pick shapes and lines (`app.objectSel`, always in one layer); Shift+click adds or takes away. Text stays with the text tool. Unfilled shapes are hit only on their outline, so you can draw inside a box. Drawing a shape picks it. With one picked, it has handles: a shape's box and turn handle, or a line's ends and a round middle handle that bends it. Several picked only move, restyle, delete, copy and line up. Changing tools lets go of the pick.
- **The options bar shows the first picked object's settings**, and changing them (or colour 1 or 2) restyles every picked object that has that setting. Loading them into the tool's settings also makes them the style for the next shape, as in PowerPoint. A run of changes to the same setting (a slider drag, arrow-key nudges) joins into one history step: `ObjectsCommand.after` is moved on while it's still the last step and the picture isn't saved there.
- **Alt** draws a shape from its centre while dragging; Alt+click without a drag still picks a colour with the Shapes tool. Shift keeps shapes square and round, turns lines and arrows in 15° steps, and keeps a move straight.
- **Snapping** (`src/tools/snap.ts`, plain maths with tests): moving snaps the box's edges and centre to other objects' boxes (text included) and the picture's edges and centre, and to equal spacing in its row; resizing snaps only the dragged edges of shapes that aren't turned; drawing and line ends snap the pointer. Within 6 screen pixels. Ctrl skips it for one drag; View > Snap to Shapes turns it off. Guides are pink (`#f0368c`), so they don't look like the blue selection.
- **Lining up**: Align (to the picked group's edges or middle) and Space Evenly (first and last stay put) are commands, shown as buttons on the options bar when two or more objects are picked (three for spacing).
- **Copy and paste of shapes**: Ctrl+C puts the shapes' picture on the clipboard for other apps and keeps the shapes; `clipboard_seq` (Windows' clipboard change count, from Rust) says whether that copy is still what's on the clipboard, so Ctrl+V pastes the shapes, and anything copied later pastes as normal. Each paste lands 16 px further down and right, as Ctrl+D does.
- **Painting on an object layer** still paints on the pixel layer under it (Phase 3), which doesn't fail silently; the plan's "offer to rasterize" is a toast the first time it happens on each layer, with a Rasterize Layer button, rather than a question that would stop every stroke after drawing an arrow. Image > Rasterize Layer turns the current object layer into pixels; Edit > Rasterize Shapes draws the picked shapes onto the pixel layer under them; Image > Flatten merges the layers that are showing (hidden ones are dropped). PNG, JPEG, WebP and BMP flatten on export as before.
- **Files**: `.sktch` is version 3 when it holds shapes or lines, so older builds refuse it rather than open it without them; text-only files stay version 2.

## Decisions for Phase 5

- **Layers** (`src/app/layers.ts`, panel in `src/ui/SidePanel.tsx`): layers gain `locked`. Rename, hide, lock and opacity are `LayerPropsCommand`s; opacity changes to one layer within 1.5 s join into one step, like shape restyles. New, delete, move and merge swap the whole list (`LayersCommand`). Changing the current layer isn't a step. A picture always keeps one pixel layer, since `paintLayer` needs one. Merge down is off when either layer is hidden or locked; two object layers at the same opacity merge as objects, anything else becomes pixels, keeping the lower layer's name and opacity (as Photoshop does). Rows are dragged with pointer events on the window, not HTML drag and drop, which Tauri's file drop handling swallows on Windows. Thumbnails redraw with the panel.
- **Locked and hidden layers** can't be painted, filled, lifted (moving, nudging, turning or deleting a selection), adjusted or picked, and new objects skip them (`objectLayerForNew`); each refusal says why in a toast. Whole-picture changes (crop, resize, rotate, flatten) still change them. A paste aimed at one goes on a new layer. `.sktch` saves `locked`; older builds ignore it, so no version change.
- **Paste onto New Layer** is a saved setting in the Edit menu, off by default. The new layer is added with the paste's canvas growth as the paste's pending step, so Esc and Ctrl+Z on the floating paste take both away.
- **Mark-up objects** (`src/engine/marks.ts`) are one object type, `mark`, with a `kind`. Each is a box turned round its centre like a shape, so `tools/shapes.ts` picks, moves, resizes, turns, restyles, copies and deletes them with the same code (`isBoxed`). The highlighter's path is stored as shares of its box, so resizing stretches it; a flip mirrors the path. Markers keep their number; deleting markers renumbers the rest of that layer, and the tool's Number follows the picture (new or opened picture, deletes, choosing the tool). A new marker takes the Number unless a marker already has it (the bar shows a picked marker's number), then the highest plus one.
- **Blur and pixelate** take their pixels from whatever is already drawn under them on the canvas being drawn, so they work the same on the zoomed view, in exports and in flatten. When marks become pixels on a layer of their own (Rasterize Layer, Rasterize Shapes, Merge Down), `drawObjects` gets a backdrop of the layers below to sample from. Blur shrinks the area by a quarter of the radius before blurring, so the detail is gone for good rather than reversible; the radius is `2 + strength × 0.18` px (about 15 px at the default 70). Pixelate's blocks line up with the box's corner, so they don't crawl as the view pans.
- **Spotlights** in a layer are drawn together, one dimming with a hole for each, so overlapping ones don't darken each other. A spotlight is only picked when nothing else is under the pointer, since what it lights up sits inside it.
- **The highlighter** has its own colours (yellow by default) instead of colour 1, which is usually black, and draws with multiply at 100% so text under it stays readable.
- **Callouts** are text boxes with a background and a `tail` point (`TextObject.tail`), so typing, wrapping, fonts and moving are the text tool's. The tail leaves the side of the box facing the point. The outline is the text colour, drawn twice as wide and then covered by the fill, so the tail joins the box with no line across it. Moving the bubble keeps the point; the round tail handle (shown while typing and with the Callout tool) moves it. Whole-picture changes move the point too.
- **Files**: `.sktch` is version 4 when it holds mark-up or callouts, so older builds refuse it rather than open it without them.
- **Adjustments** (`src/engine/adjust.ts`, `src/app/adjust.ts`) are canvas filters (`brightness`, `contrast`, `hue-rotate`, `saturate`, `grayscale`, `invert`), which Chromium runs on the GPU: previewing a 3840 × 2160 layer costs 0.6 ms a frame against 0.2 ms without, so no WebGL pass or worker is needed. The whole-layer preview draws the layer through the view's own filter; a selection's preview draws the changed area over it. They change the selection (masked by its outline), a lifted or pasted selection's pixels, or else `paintLayer`. Auto Level ignores the outer 0.5% and see-through pixels and stretches all three channels by one range, so greys stay grey (per-channel stretching tinted grey screenshots); it reads pixels on the main thread and takes about 0.23 s on 4K. Adjust is its own menu; Invert is Ctrl+Shift+I and Auto Level Ctrl+Shift+L, as in Paint.NET.

## Decisions for Phase 6

- **Data folder.** Autosaves, update builds and installers live in `%LOCALAPPDATA%\app.sketch.desktop` (Tauri's app local data folder, apart from the install folder `%LOCALAPPDATA%\Sketch` so an update never takes them; since 1.2.0 an uninstall removes it unless the person keeps it, see the uninstall section at the end). `--data-dir=…` or `SKETCH_DATA_DIR` moves it; every check sets it, so checks never touch the user's autosaves or updates.
- **Autosave** (`src/app/recovery.ts`, `src-tauri/src/recovery.rs`): each window has a slot, `<id>.json` (what's open, whether it's unsaved) and `<id>.sktch` while there are unsaved changes, written 3 s after a history change (later if a stroke or drag is in progress). It saves the whole picture as `.sktch`, not changed tiles only as the plan said: PNG encoding runs in the encoder worker, and on a 4K picture the main thread had no pause over 50 ms during an autosave, so tiles weren't worth the extra format. A clean picture with a file keeps only the `.json` (reopened from disk); a clean blank picture keeps nothing. Undo history isn't kept. Slots left by an earlier run go to the first window that asks (`recovery_orphans`, once per run): one opens there, the rest in windows of their own.
- **Closing** asks Save or Don't Save when there are unsaved changes, the same box New and Open use; clicking outside it or Esc cancels. Both delete the slot. Until 22 Oct 2026 it also had Cancel and Keep for Next Time buttons (keep the slot for the next run), which the user found too many.
- **One running Sketch** (`src-tauri/src/instance.rs`): a named pipe named after the data folder (FNV hash), not `tauri-plugin-single-instance`, which keys on the app id and so would hand a check's launch to the user's running Sketch. The first process serves the pipe; a later one sends `{args, cwd}` and exits. The window used last (tracked from focus events) gets a `launch` event and decides: a paste or a file goes in a new window, unless that window holds an untouched new picture, or the "Open files from Explorer in the window used last" setting is on (files only). New windows are built in an `async` command (a sync one deadlocks on Windows), labelled `w2`, `w3` and so on; capabilities apply to `*`.
- **Explorer** (`src-tauri/windows/hooks.nsh`, NSIS hooks): Tauri's `fileAssociations` sets the default program for an extension (it overwrites `.ext`'s default value), so it's used only for `.sktch` and `.qpaint`. Pictures get `OpenWithProgids` (`Sketch.Picture`), `Applications\sketch.exe\SupportedTypes`, an "Edit with Sketch" verb under `SystemFileAssociations` and a `RegisteredApplications` entry for Settings > Default apps, without changing what opens them. The verb is in Windows 11's classic menu only: the new menu needs a packaged app with an identity, which needs signing. The uninstaller removes it all, except when an update runs it with `/UPDATE`.
- **Jump list**: the process sets its AppUserModelID to the installer shortcut's (`app.sketch.desktop`), and opening or saving a file calls `SHAddToRecentDocs`. Not with a data folder override, so checks keep their test files out of the user's recent files.
- **Paste shortcut**: a Start menu shortcut, `Paste into Sketch.lnk` with `--paste` and a hotkey, made by PowerShell's `WScript.Shell`. Windows runs it from anywhere even with Sketch closed, which a global hotkey registered by Sketch couldn't do without staying in the background. Keys must be Ctrl with Alt or Shift and a letter, digit or F key.
- **Build stamp**: `scripts/build-info.mjs` stamps the commit, its subject, the build time and the main checkout's path (`git rev-parse --git-common-dir`, so a worktree build points at the real repo) into the page as `__SKETCH_BUILD__`. Help > About shows it. Uncommitted changes aren't marked, so a local build of HEAD with edits says HEAD.
- **Updates** (replaced by Silent Updates, F6, below; kept for what a Sketch from before it still does) (`src-tauri/src/update.rs`, `src/app/update.ts`, `scripts/update-build.mjs`), the design of another of the author's apps: watch `refs/remotes/origin/main` for the newest commit touching `sketch/` (at start after 4 s, every 5 min, on focus); newer means not an ancestor of the running commit. The build runs in a detached worktree (`build/sketch-update-build`, cleaned with `git clean -fdx` except `node_modules` and `target`), as a detached Node process out of the app's job, so closing Sketch doesn't stop it. `build.lock` is touched every 10 s and counts as dead after 90 s. `npm ci` runs when `package-lock.json`'s hash changed. `latest.json` holds the commit, subject, build time, file and SHA-512; only the newest installer is kept. A failed build writes `last-error.json` and that commit isn't tried again. Installing checks the SHA-512, has every window flush its slot (8 s limit), starts a hidden PowerShell that waits for Sketch to exit and runs the installer with `/S /UPDATE /R` (silent, no new shortcuts, start Sketch after), and quits. A failed install restarts the old Sketch and leaves `install-error.txt`, shown at the next start. The first start of a new build shows "Updated to …". Dev servers and the browser build never check.
- **Downloading update** (F4, taken out by F6.4): `update_status` reports `building` (and its subject) only for a live lock on a commit newer than the running one, so a stale lock from an older build shows nothing. The page shows the greyed-out button only while nothing is ready (a ready older build keeps "Update available"), with `aria-disabled` rather than `disabled` so the tooltip still gets pointer events, and no click handler. Checks are a `setTimeout` chain: 10 s while building, 5 min otherwise. A failed build removes its lock, so the next check hides the button.
- **Paste speed**: pasting into a new picture used to read every pixel back from the GPU before showing it, to choose the canvas fill (white unless the image has see-through pixels); the first readback costs about 200 ms on 4K. The fill is now worked out 250 ms after the paste shows, since it only matters once the canvas grows.
- **Checks**: `check:speed` times the goals in the real app; `check:fuzz` runs random commands, drags, undo and redo with a seeded random number generator and validates the document after each step; `check:update` tests updates against a throwaway clone (the working tree's Sketch changes committed in it, then a pushed commit), and with `--install` installs, updates and reinstalls for real.

## Decisions for Whiteboard Mode (F1)

- **A whiteboard is a `PaintDocument` with `board` set** (`src/engine/board.ts`), not a new tile store. The plan said to keep strokes in tiles made only where something is drawn; that would mean rewriting every pixel tool, fill, selection, adjustment and undo around sparse storage. Instead each pixel layer stays one canvas that starts at 2048 × 2048, see-through, and grows when a pixel tool starts where it doesn't reach. Shapes, text and mark-up already have no size, so they sit anywhere, off the canvas too; the renderer doesn't clip a board to its canvas.
- **Growth** (`boardGrowth`): at pointer-down, the brush, pencil, eraser, fill and the select tools make the canvas hold what's on screen within 3072 px of the pointer (`growBoardForPointer` in `src/app/board.ts`). It grows past that by a 1024 px margin, in whole 256 px tiles, so a board doesn't grow on every stroke and the dot grid (spaced 32 to 256 px) stays put. Over `MAX_SIZE` it drops the margin, then grows only as far as it can, with one toast. Growing up or left is `resizeCanvas` with an offset, wrapped in `BoardGrowCommand`, which moves the view the other way (and `app.lastPoint`) on apply, undo and redo, so the board never jumps on screen. Pastes and drops grow the board to hold the picture; rasterizing, flattening and merging grow it to hold the shapes first, so nothing off the canvas is cut off.
- **One undo step**: a growth is marked `joinNext`, and `History.record` folds it into the next step (a stroke, a paste), so one Ctrl+Z takes both away. A fill refused on open space takes its growth back with `History.discardTop`.
- **On screen**: the board is white (`BOARD_BACKGROUND`) in light and dark mode, as pictures are, with a dot grid drawn only on screen. No size handles, pixel grid or pan limits. Pointer positions aren't shown, since a board's pixel positions move as it grows; the status bar says Whiteboard.
- **Hidden tools**: `AppCommand.hidden` takes Crop to Selection, Crop, Resize, Canvas Size, Trim to Content and the Crop slot out of the menus, palette, rail and shortcuts on a board. Rotate and Flip stay but need a selection.
- **Fill** refuses an area that reaches the canvas edge, since the board's empty space runs on past it; filling inside closed outlines works as on a picture.
- **Fit** (Ctrl+0 and the status bar button) zooms to fit everything on the board, at most 100%; an empty board shows its middle at 100%. `contentBounds` reads every visible pixel layer back to find painted pixels (`alphaBounds`), so it's only run on demand.
- **Export and copy**: PNG, JPEG, WebP, BMP and copying the whole board flatten what's on it (`exportArea`: everything showing plus 24 px) onto white with `flattenArea`. A spotlight counts only its own box, since its dimming has no end. An empty board refuses to export or copy. Saving to a flat format asks first, as layers do, with "Save Picture" in place of "Merge and Save".
- **Files**: `.sktch` is version 5 with `board: true`, so older builds refuse a whiteboard rather than open it as a picture. A new whiteboard is never treated as an untouched New picture, so a paste or an opened file doesn't replace it.

## Decisions for the Mouse Sensitivity Slider (F2)

- **Only while drawing** (23 Oct 2026). The user saw no reason for the slower speed outside a stroke, so it no longer follows the pointer over the window. The canvas tells Rust when the left mouse button goes down on it (`mouse_drawing`, sent only for a mouse, not a pen, and only when the slider isn't at normal), and the speed applies from then until the button comes up. Panning (middle button or Space) and right-button strokes stay at normal speed. The worker checks every 20 ms that a Sketch window still has focus and the primary button is still down (`GetAsyncKeyState`, with `SM_SWAPBUTTON` for swapped buttons), and ends the stroke itself when it isn't, so a lost `pointerup` can't leave the slower speed for the next click elsewhere. The stroke keeps the slower speed past the window's edge, since the canvas keeps the pointer until the button comes up. Between strokes the thread is parked. The bullets below describe the hover rule it replaced, which still holds for everything except when the speed applies.

- **Left Ctrl only** (24 Oct 2026, later the same day). The user wants Left Ctrl to be the only way the slower speed comes in: a stroke without Ctrl keeps their own speed. The canvas no longer tells Rust about strokes (`mouse_drawing` and the button check are gone), so the worker follows only `mouse_ctrl` and `VK_LCONTROL`, and `mouse_speed_force` takes only `ctrl`. The two bullets below describe the stroke rule this replaced; their focus test, polling and Ctrl details still hold.

- **Hold Left Ctrl for the slower speed** (24 Oct 2026). The user wanted the slower speed for lining the pointer up before a stroke, not only during one. Left Ctrl was picked because no tool gives Ctrl a meaning of its own with a click or drag: Shift (straight lines, keep ratio, add to the pick, opening a capture), Alt (colour pick, brush size, the menus) and Space (pan) are taken. Its one overlap is that Ctrl already skips snapping while drawing or dragging shapes, lines, arrows and marks, which the user accepted. Only while a Sketch window has focus, as the user asked; the capture overlay isn't covered. The page tells Rust when Left Ctrl goes down or comes up (`mouse_ctrl`, by `code === 'ControlLeft'`, so Right Ctrl does nothing, and only when the slider isn't at normal; key repeats count, so a window that takes focus with Ctrl already down picks it up). The worker then checks `VK_LCONTROL` with the same focus test as the button, and ends the hold itself when Left Ctrl comes up or Sketch loses focus. Ctrl shortcuts bring the slower speed in for the moment Ctrl is down, which nobody notices unless the mouse moves then. `mouse_speed_force` takes `ctrl` beside `held` for checks.

- **Hover and focus, measured.** The plan asked whether following the pointer was worth its cost, against applying the speed whenever a Sketch window has focus. A worker thread in Rust (`src-tauri/src/mouse.rs`) checks every 20 ms whether the foreground window is a Sketch window (same process, not a `#32770` dialog such as Open or Save) and the window under the pointer (`WindowFromPoint`, then `GA_ROOT`) is that window. The full check costs 2.9 µs (`pointer_check_cost`, release build), so 50 checks a second are about 0.015% of one core. Over 15 s, `sketch.exe` used 78 ms of CPU with the slider at normal and 78 ms with it at 50% (the difference is under `Get-Process`'s 15.6 ms resolution). It reads no input and hooks nothing, so it can't add input lag or stutter. So the speed applies only while the pointer is over a focused Sketch window, as the user wanted. The thread sleeps (`thread::park`) whenever the slider is at normal and nothing is applied.
- **No mouse hook.** A low-level mouse hook (`WH_MOUSE_LL`) would see every pointer move instantly but sits in the input path of every app on the PC. Polling at 20 ms leaves at most 20 ms at the wrong speed when crossing the window's edge.
- **The slider counts Windows' own speed steps** (1 to 20, default 10) from the user's own speed, from 6 below up to the user's own speed (25% to 100% at the default speed; until 22 Oct 2026 it went 4 above, to 200%, but the user saw no use in a faster mouse), so every position is a real Windows speed. The percentage comes from Windows' multiplier for each step (with "Enhance pointer precision" off, 1/32 at step 1 up to 3.5 at step 20). Offset 0 never touches the setting.
- **Safe restore.** `SPI_SETMOUSESPEED` is called with flags 0: not written to the profile (a crash can't outlast signing out) and not broadcast (other apps aren't sent `WM_SETTINGCHANGE` each time the pointer crosses the edge). Before each change, the user's own speed and the speed set go to `mouse-speed.json` in the data folder; putting the speed back deletes it. At start, a leftover file means the last run didn't put it back, so Sketch does, but only if the speed is still the one Sketch set. A speed changed meanwhile (by the user in Windows settings) is never overwritten: putting back checks the same way, and while Sketch's speed is in force a different reading becomes the user's own speed. `RunEvent::Exit` puts it back on every clean close, including an update's.
- **One setting for every window.** The slider is a saved setting (`sketch.mouseSpeed`) shared by all windows; the Rust side holds one offset, and other windows follow the change through the `storage` event.
- **Checks never change the real speed**: `SKETCH_TEST_MOUSE_SPEED` points the Rust side at a stand-in file (the driver sets it for every launch), and `mouse_speed_force` (test hooks only) says whether Left Ctrl is held (until 24 Oct 2026 also the primary button, and until 23 Oct 2026 whether the pointer was over Sketch), so `check:native` reads no real keys or mouse; its keys and strokes go to the page through the debugging port. `real_setting_round_trip` (ignored test) checks the real Windows calls by changing the speed one step for a moment.

## Decisions for Built-In Screen Capture (F3)

- **GDI, not Windows.Graphics.Capture.** The plan said "the Windows capture API". `BitBlt` of the whole virtual desktop with `CAPTUREBLT` (`src-tauri/src/capture.rs`) gives every monitor at its physical pixels in one call, includes layered windows (tooltips, menus), shows no yellow capture border and needs no Direct3D. Windows.Graphics.Capture works one monitor or window at a time and is asynchronous. The process is made per-monitor DPI aware (v2) at the top of `run()`, before Tauri, so positions are physical pixels on every monitor.
- **A native overlay, not a webview.** The frozen picture is shown by a plain Win32 popup (`SketchCapture` class, topmost, no fade-in) covering the virtual desktop, on a thread of its own with its own message loop. It draws the frozen pixels one to one, so nothing is scaled whatever each monitor's scale is, and it needs no WebView2 start-up. The overlay appears 167 to 248 ms after the capture shortcut starts Sketch, and 187 to 233 ms when Sketch is already open (5 runs each, release build, three monitors totalling 6200 × 1920). The screen is frozen before the overlay shows, so the picture is the moment the keys were pressed.
- **Picking**: hovering highlights the window under the pointer (or the screen, over the desktop); a click takes it, a drag of 4 px or more takes an area, F or Enter takes the screen under the pointer, Esc or a right-click cancels. Windows are listed with `EnumWindows` before the overlay shows, top first, by their frame without the shadow (`DWMWA_EXTENDED_FRAME_BOUNDS`); cloaked, click-through, fully see-through and the desktop's own windows are left out, so invisible overlays from other apps can't be picked. Outside the highlight the picture is shown at 45% brightness; the border sits just outside a dragged area, so it never covers an edge being lined up, and (since 22 Oct 2026) just inside a highlighted window or screen, since outside it spilled onto the next monitor or off the screen for a maximised window. It's never in the shot. A size label and a one-line hint are drawn in Segoe UI at each monitor's scale. State lives in a `thread_local`, and calls that can send a message straight back (`SetCapture`, `ReleaseCapture`, `DestroyWindow`) are made after the state is let go.
- **Sketch hides itself first** (only with "Hide Sketch when capturing" on since 22 Oct 2026; see F10 below) when the capture starts from inside it (the toolbar button, File > Capture Screen, the palette) or when the shortcut is pressed while a Sketch window is in front. Windows fades a window out when it's hidden, and the screen was frozen mid-fade with Sketch still in it, so the fade is turned off (`DWMWA_TRANSITIONS_FORCEDISABLED`) while hiding and on again after; three `DwmFlush` calls then wait for the desktop to redraw. Asking each window `is_visible` after `hide` makes sure Tauri's main thread has hidden them.
- **The shortcut is a Start menu shortcut**, `Capture with Sketch.lnk` with `--capture`, made the same way as the paste shortcut (`shell.rs`, now one `set_shortcut` command for both kinds). The plan expected a background start-up from 6.2 and a global hotkey registered by Sketch; 6.2 chose the Start menu shortcut instead, because Sketch doesn't stay running in the background, and Windows runs the shortcut with Sketch closed. It's off until the user picks keys in Settings, like the paste shortcut. Before making it, `set_shortcut` refuses keys the other shortcut has, then tries `RegisterHotKey` with them: if that fails, another app holds them and the error says so. A cold start with `--capture` freezes the screen before Tauri starts. The window it starts stays hidden (`appReady` waits) until `capture_wait` hands it the capture; cancelling quits Sketch. With Sketch already running, the second process passes the foreground on (`AllowSetForegroundWindow`) so the overlay gets the keys.
- **Opening**: the capture goes on the clipboard from Rust (`arboard`, so PNG with transparency), is kept by id in `Shots`, and is delivered as a `Launch` with `capture` set, like a paste: an untouched New picture takes it, otherwise a new window opens. The window reads it once with `capture_take` and pastes it into a fresh picture (`pasteImage`, so the canvas is the capture's size and undo, save and export work as on any picture), then picks the Brush in the palette's red (`CAPTURE_COLOR`, `#ed1c24`). Until 22 Oct 2026 it picked the Arrow tool.
- **Checks** (`check:native`) drive the overlay with posted mouse and key messages (`overlay` in `native-driver.mjs`), never the real mouse, and capture a borderless magenta window shown by a PowerShell process: a drag over where Sketch's window was must give only magenta. Mixed display scales aren't tested: this PC's three monitors all run at 100%.

### Toolbar and notification (22 Oct 2026)

The user found the hover highlight distracting while lining up an area, and wanted the Snipping Tool's flow: the capture goes on the clipboard with a notification, and only a click on it opens Sketch.

- **A toolbar instead of guessing.** Four buttons drawn by the overlay itself (GDI, same thread): Area (the default), Window, Full screen, Close. Only Window and Full screen highlight what's under the pointer; Area dims everything until a drag. The toolbar sits at the top centre of the screen the pointer was on, at that screen's scale, with a tooltip under the hovered button. It hides while a dragged area comes within 8 px of it. At first it also hid under a highlighted window or screen, which in Full screen mode hid it almost always, so the user asked for it to stay: in Window and Full screen modes it always shows, and nothing is highlighted or picked under it. It's never in the shot, which comes from the frozen picture. A click without a drag in Area mode does nothing, as in the Snipping Tool. F, Enter, Esc and right-click keep working. Checks pick a mode with the overlay's own `WM_SET_MODE` (`WM_APP + 1`) message.
- **A WinRT toast, not a plugin.** `note.rs` calls `ToastNotificationManager` through the `windows` crate (already a dependency) under the app id `app.sketch.desktop`, which the installer's Start menu shortcut carries. The click arrives as the toast's `Activated` event in the running process, so no COM activator or registry entry is needed; the price is that a toast clicked after Sketch quit would do nothing, so `close_all` on exit removes Sketch's toasts (its own group, `capture-<pid>`, so a check's Sketch never removes the user's). Toasts dismissed by the user drop their capture; timed-out ones stay clickable in the notification centre. Only the newest five captures are kept, since each waits in memory. `ToastNotifier.Setting()` fails with "Element not found" for an app known only by its Start menu shortcut, so only a clear answer other than Enabled counts as off. If Windows refuses (notifications off for Sketch, or `Show` fails), the capture opens at once as before.
- **The picture in the toast** is a PNG of at most 728 px a side, averaged down from the capture (`png` crate, already in the build through `arboard`), written to `<data folder>\captures` and deleted when its toast ends.
- **No sound** (24 Oct 2026). The toast carries `<audio silent="true"/>`: the user knows it's coming after a capture and found the sound distracting. It still pops up, and other apps' notifications keep their sound.
- **Cold starts wait hidden.** With Sketch closed, the shortcut's process keeps its hidden first window waiting in `capture_wait` until the toast is clicked, dismissed, or 30 minutes pass, then quits (or closes only that window if another was opened meanwhile). `deliver` now passes over hidden windows, so a capture clicked in that time opens in a window of its own.
- **Checks** click the newest toast with `capture_click_note` (test hooks only), and their toasts skip the pop-up (`SuppressPopup`) so a run doesn't flood the screen. The real click, and whether Windows lets the new window come to the front after it, is only tested by hand.

## Decisions for Background Capture (F7)

The plan was written before the toolbar and notification above, and before Silent Updates (F6), which it depends on, was built. What changed from it, and why:

- **A helper process, `sketch-capture.exe`**, a second binary of the same Cargo package (`src/bin/sketch-capture.rs`, the code in `src-tauri/src/helper.rs`). The plan said to move the capture code into a crate of its own; a second binary of the package shares `capture.rs` and `note.rs` without moving them, and since it never calls into Tauri, link-time optimisation leaves Tauri out: the exe is 476 KB. `tauri build` builds every binary of the package (`--bins`), and the installer hooks copy it in (`!searchreplace` on `MAINBINARYSRCPATH`), since it isn't one of Tauri's bundled files. It has no window anyone sees: a hidden top-level window (class `SketchCaptureHelper`, titled `sketch-capture-<hash of the data folder>`) holds the keys with `RegisterHotKey`, and is how Sketch and the installer find it and tell it to quit (`WM_CLOSE`). A named mutex keeps one helper per data folder, so checks never meet the user's.
- **The helper runs whenever capture has keys, with Sketch open or closed.** One code path for the keys: a `HKCU\…\Run` entry named "Sketch Capture" starts it at sign-in and Sketch leaves it running when it quits. Checks write a stand-in file (`run-entry.txt` in their data folder) instead of the registry. Until 22 Oct 2026 a "Keep capture ready when Sketch is closed" switch could make Sketch stop the helper as it quit; the user found it one setting too many and it went (see "One capture shortcut" below). An old `capture.json` still holding `background` reads fine, and Sketch's start puts the Run entry back.
- **Who captures.** With Sketch in front (the foreground window's process is this install's `sketch.exe`), the helper hands `--capture` to Sketch over its pipe (`instance::send`), so Sketch hides its windows first as before. Otherwise the helper captures itself: the overlay, the clipboard and the notification, under the same app id. Its notifications outlive Sketch, which was the point: before, a cold-start capture's notification only worked for 30 minutes and only while a hidden Sketch waited.
- **Captures wait on disk, not in memory**: the helper writes each capture as raw RGBA after an 8-byte size header to `<data folder>\captures\<pid>-<id>.rgba` (no compression, so writing and reading it is quick) and drops it from memory, so it holds 3.1 MB of private memory while it waits (24.6 MB working set, mostly shared system DLLs). Clicking the notification starts `sketch.exe --open-capture=<file>` (or hands it to the running Sketch); Sketch reads the file into `Shots`, deletes it, and opens it like any capture. A dismissed notification deletes its file; files older than a day are deleted when Sketch or the helper starts.
- **After a capture**: the plan's setting, but with "Copy it and show a notification" as the default, since the user had already made that the behaviour on 22 Oct 2026. "Open it in Sketch" opens straight away, from the helper, the camera button and the cold start alike. The helper reads the setting at each capture, so a change needs no restart.
- **Print Screen.** `RegisterHotKey(VK_SNAPSHOT)` succeeded on this PC with Windows' setting at its default (on), so the call can't tell whether Windows has the key, and Sketch checks the setting itself: `HKCU\Control Panel\Keyboard\PrintScreenKeyForSnippingEnabled`, which Windows only writes once someone changes it; missing means on from Windows 11 build 22621, where the default changed. Plain Print Screen is refused while it's on, with a button that opens `ms-settings:easeofaccess-keyboard`. Windows sends Print Screen to the page only on key up, so the key picker listens for that.
- **Which keys.** `RegisterHotKey` takes any modifiers, so capture keys aren't held to the Start menu shortcut's "Ctrl with Alt or Shift": any two or more of Ctrl, Alt and Shift with a letter, digit or F key (`isCaptureHotkey`). One modifier is refused, since Alt+letter opens menus and Ctrl+letter is every app's own shortcut. Until 22 Oct 2026 the page still used the Start menu rule, so Alt+Shift+S was refused, and the user bound it to File > Capture Screen in the in-app shortcuts instead, where it only worked with Sketch in front.
- **One capture shortcut (22 Oct 2026).** The user wanted one key for capture that just works, not an in-app shortcut, a Windows-wide key and a background switch. Capture Screen's row in the keyboard shortcuts list is now the capture key: recording it checks `isCaptureHotkey` and calls `set_shortcut('capture')`, and the key lives only in the helper's `capture.json`, never in the page's `sketch.keys` (`CAPTURE_ID`, `captureKey` and `setCaptureKey` in `commandList.ts`). It still joins the page's bindings, so menus and the shortcuts sheet show it and it takes the key off any other command; if the helper isn't running, the page's own key handling still captures while Sketch is in front. The Settings key picker listens on key up too, since Windows sends Print Screen only then. As each window starts, `startCaptureKey` reads the helper's key; when there's none and `sketch.keys` holds an older in-app Capture Screen key that Windows can hold, that becomes the capture key, and the in-app copy is dropped either way. The General section keeps only "After a capture" and the paste key.
- **The old Start menu shortcut goes.** Its keys would clash with the helper's, so the first Sketch start (only with the real data folder) moves its keys to `capture.json` and deletes `Capture with Sketch.lnk`. `--capture` still works for anything that starts Sketch with it.
- **The helper's place in the installer.** Tauri `!include`s `hooks.nsh` before it defines `MAINBINARYSRCPATH`, so the `!searchreplace` that turns that path into the helper's must sit inside `NSIS_HOOK_POSTINSTALL`, which expands later. At the top of the file it found nothing to replace, and every installer until 22 Oct 2026 copied `sketch.exe` in as `sketch-capture.exe`: Sketch then started a second Sketch as its "helper", which handed over and quit, so capture keys never worked and Settings said the helper didn't start. `check:native` runs the built exes and never saw it. An `!error` now stops the build if the two paths match; to check an installer by hand, unpack it with 7-Zip and compare `sketch-capture.exe` (about 475 KB) with `target/release/sketch-capture.exe`.
- **Updates and uninstall.** The installer's pre-install hook closes every helper so its file can be replaced (`SetOverwrite try`, so a helper that won't quit can't stop an install), and the post-install hook points the Run entry at the new install and starts the helper again. Uninstalling closes it and removes the exe and the Run entry. Since F6 the helper lives in each version folder and the Run entry goes through the launcher (see Silent Updates below).
- **Speed.** With Sketch closed, the overlay shows 105 to 126 ms after the keys (3 runs, release build, three monitors), where a cold start of Sketch from the old Start menu shortcut took 167 to 248 ms.
- **Checks** drive the helper with its own test messages (`WM_TEST_KEYS`, `WM_TEST_CLICK`, test hooks only) instead of pressing keys, and reach the Sketch it starts through the debugging port that Sketch inherits from the check's first launch (`attach` in `native-driver.mjs`). Not checked automatically: the real key press, Sketch in front at the moment of the keys (the check takes whichever path the focus gives it and says which), signing out and in, and timing against the Snipping Tool.

## Decisions for the Copy Button (F8)

- **The same action as Ctrl+Shift+C** (`actions.copy(true)`, which now says whether it copied), so layers, shapes, arrows, text and a placed or floating paste are all merged, a whiteboard copies its drawing cropped as an export does, and the picture stays editable. The button sits after the camera button and is shown in the browser build too, since copying works there.
- **The only button left at the right of the menu bar besides the panel button** (22 Oct 2026). The user uses Copy most there and kept mis-clicking its neighbours, so the camera button was removed (capture is driven by its keys, File > Capture Screen and the palette), and the mouse speed and command palette buttons moved to a group of their own at the bottom of the tool rail, search last. The mouse speed slider now opens to the right of its button, bottom-aligned with it.
- **"Copied" on the button** for 1.5 s: the icon turns into a tick and the word shows beside it in the accent colour, so it's clear before switching apps. The toast the command already shows stays too.

## Decisions for Closing Quick Captures Without Asking (F9)

- **Which captures.** A capture is quick when it was opened by a click on its notification, whoever showed the notification: the helper (`--open-capture=… --from-note`), Sketch's own (`start_capture`'s click handler) or a cold start's (`capture_wait` returns `{ id, quick }`). The plan also said captures taken from inside an open Sketch keep the dialog; it was written as if those open straight away, but with the default "After a capture" they also go through the notification, so the rule is the plan's own test: opened from the notification or not. Captures that open at once ("Open it in Sketch", or Windows refusing the notification) aren't quick.
- **Where the mark lives.** `Launch.quick` carries it from Rust to the page, and `openCapture` sets `app.quickCapture` after pasting. It's never written into a `.sktch` file or an autosave slot, so a capture brought back after a crash asks as usual. `setDocument` (New, Open, a recovered slot) and every successful save (`writeAs`) take it off.
- **Closing.** `onCloseRequested` skips `confirmLoseChanges` for a quick capture and then deletes its slot with `discard`, as Don't Save does. Each window has its own page, so only that window closes without asking.

## Decisions for the Setting to Hide Sketch When Capturing (F10)

- **Saved in `capture.json`**, as `hide`, beside "After a capture", since the Rust side decides before the screen is frozen and the helper's handover reaches Sketch without the page. A file without it (every install before 22 Oct 2026) reads as off, the plan's default for everyone. `capture_options_set` takes `after` and `hide` as optional, so changing one leaves the other.
- **One check in `start_capture`**: Sketch's windows are hidden (with the fade turned off and `wait_for_screen`) only when the caller asked to hide and the setting is on. That covers the camera button, File > Capture Screen, the palette, and the helper's handover (`--capture` while Sketch is in front). With Sketch closed there's nothing to hide.
- **The switch** is a checkbox row in Settings > General, under "After a capture" (`data-setting="captureHide"`).

## Decisions for the colour theme setting

- **Same as Windows, Light or Dark**, at the top of Settings > General (`src/app/theme.ts`), saved as the `theme` setting and shared by every window: a change in one reaches the others through the `storage` event (`onPrefChanged` in `prefs.ts`). Same as Windows is the default, so nothing changes for anyone who never opens it.
- **Dark colours hang off `html.dark`**, not a `prefers-color-scheme` media query, so a forced theme works in a plain browser too. `theme.ts` sets the class before the first render and tells the canvas (`onThemeChange`) to re-read its colours.
- **The window follows**: `getCurrentWindow().setTheme()` (permission `core:window:allow-set-theme`) sets the frame's dark mode, which Mica follows (`apply_mica` is called with `None`, so it never fixes the colour itself), and Tauri passes the window's theme on to WebView2, so `prefers-color-scheme` in the page then reports the forced theme. Same as Windows sends `null`, and the window's frame and the page's media query go back to the system setting; `theme.ts` listens to that media query, which is how a Windows change reaches the page.

## Decisions for start-up tool and window place (22 Oct 2026)

- **Every window starts with the Brush in black** (`tools.current` starts at `DEFAULT_TOOL`; the last tool is no longer saved, though each slot's last tool and every tool's settings still are). A capture opened from its notification picks the Brush in red. Before, the last tool came back, which after a capture was the Arrow.
- **The window's place lives in Rust** (`src-tauri/src/place.rs`), in the data folder's `window.json`: outer top-left and inner size in physical pixels, plus whether it was maximised. Rust places each window while it's still hidden, so it never shows at the wrong place first. The page shows its window with `show_window`, which maximises it first if it was. Only moves and resizes of a visible, unminimised window count (so setting up a hidden window, or hiding it for a capture, saves nothing), and a maximised window keeps the place it restores to. Writes wait 500 ms after the last move, and the newest place is written again at exit. Further windows open 32 logical px down and right per other open window. A place whose title bar middle isn't on any screen's work area opens centred; a size bigger than that work area is cut down to it.
- **Updates and checks don't move it**: the data folder survives installs, and every check runs with `SKETCH_DATA_DIR` set, so it has its own `window.json`.

## Decisions for Silent Updates (F6) and the Update Ready Icon (F11)

Another of the author's apps built the same feature first, and these follow its design and the fixes its first real updates needed. What changed from the plan, and why:

- **The launcher is a third binary of the package** (`src/bin/sketch-launcher.rs`), not a crate of its own as the plan said, for the same reason as the capture helper: `tauri build` builds and bundles every binary, so the installer copies it in with no extra step, and it shares the package's icon and manifest resources. It uses no crates (kernel32 and user32 by hand), the Windows subsystem and is 288 KB. It's that app's launcher with Sketch's names: `current.json`'s `folder` first, then other version folders newest `builtAt` first (from `version.json`, which needs both programs beside it), `--launcher-fallback=<folder>` when it falls back, `--wait-pid` (2 minutes, the other app's limit, not the plan's 30 s), and clean-up that renames a folder to `.trash-<name>` before deleting it, so a version with a running program inside is never half deleted. It keeps current, previous and the one it started. It passes the caller's working folder on (so a relative file name opens) unless that folder is inside the install folder, which would keep a version folder from being deleted. With nothing it can start, it says so in a message box.
- **The capture helper is versioned too.** It lives in each version folder; the `Run` entry is `"<install>\sketch.exe" --capture-helper`, which the launcher turns into the current version's helper. A Sketch that finds a helper running from another folder (`helper_path`) stops it and starts its own, so a restart into a new version updates the helper. The helper opens captures through the launcher, and "Sketch is in front" means any `app-*\sketch.exe` of the install (`layout::is_sketch_exe`), not one path.
- **Staging is the build script's** (`update-build.mjs` with a fourth argument, the install folder): `tauri build --no-bundle`, copy both programs to `app-<short>.part`, compare SHA-512, write `version.json`, rename, swap the launcher in when its bytes differ (`sketch.exe.old` beside it, which the launcher deletes), then write `current.json` whole with `previous` set to the folder it named before, and remove version folders other than those two (one in use stays). Without the fourth argument it builds the installer and `latest.json` as before: a Sketch from before F6 runs the new commit's script with three arguments, so its last "Update available" installs the installer that moves it to the launcher layout. That's the one-time switch-over, with nothing extra for the user.
- **Only a Sketch running from the layout updates itself** (`layout::install_root`: its folder is `app-*` with `sketch.exe` beside it). Dev builds and `target/release` never build or restart.
- **The installer** (`hooks.nsh`): Tauri copies `sketch.exe`, `sketch-capture.exe` and `sketch-launcher.exe` into `$INSTDIR`; `SKETCH_LAYOUT` moves the first two into `app-<short commit>` (from `version.nsh`, which `build-info.mjs --nsis` writes before each build; the build stops if it's missing), renames the launcher to `sketch.exe` and writes `version.json` and `current.json`. Everything outside keeps pointing at `$INSTDIR\sketch.exe`, now the launcher, so shortcuts, verbs, file types and the uninstall entry needed no change. Reinstalling the same build keeps a running copy. Uninstalling first closes any Sketch running from a version folder (Tauri's own check only sees the launcher), then `SKETCH_REMOVE_VERSIONS` removes every `app-*` and `.trash-*` folder and `current.json`. The data folder stayed until 1.2.0 (see removing the data folder on uninstall, at the end).
- **The quiet restart** (`update.rs`) checks every minute: a version is staged, no Sketch window is in front, no capture is on screen or waiting for its notification (its picture lives only in memory), no Sketch dialog box is open (`#32770` windows of the process), and no input for 5 minutes (`GetLastInputInfo`) or a locked screen (`OpenInputDesktop` fails). 5 minutes, not the plan's 10: the other app moved to 5 after its first days, since that's past nearly every reading pause. Then each window gets `update-prepare` with `quiet`, and calls it off if it's busy (a dialog, typing, a stroke or drag, a selection not yet placed, a crop or adjustment preview); otherwise it saves its slot, including an empty window's (`blank`), so every window comes back. Sketch writes `restart.json` (each slot's `GetWindowPlacement`: normal rectangle, maximised, minimised), starts the launcher with `--wait-pid` and `--quiet-restore` (or `--restart` from the menu), and exits.
- **Coming back without the focus.** Tauri's `show` activates the window and its window state goes wrong if it's shown with Win32 behind its back, so `show_window` sets the normal rectangle with `SetWindowPlacement` while the window is still hidden, shows it, maximises or minimises it as it was, and then hands the focus back to the window that had it (the other app's `blur`). A window from a restart waits to show until its picture is back (`restart` in the launch, released like a capture's), so it can be placed by the slot it reopened (`recovery_claim` records which). Slots come back in the windows' order, and quiet restores show no "Brought back" message.
- **Restart to Update** is in the Help menu (and the palette) only while a version is ready; there's no question first, since every window's picture comes back. The update buttons, the PowerShell install helper, `update_install`, the "Updated to …" note and the install error note went; Sketch deletes what they left in the data folder's `updates`.
- **The icon** (F11, `st-update` in the status bar, Lucide's `CircleArrowUp` at 14 px with the status bar's 1.75 stroke) is a plain `span` with `role="img"` and `aria-label="Update ready"`, no tooltip or handler, in the status bar's `--muted` colour. It shows while `update.ready` is set, which is only once the folder is staged, never while building. Checks stay every 10 s while a build runs (not every 5 minutes as F6.4 said), so the icon shows within seconds of staging.
- **Checks.** `check:update` now runs everything in a scratch install folder and never installs: the installer's two macros compiled into a small test installer with Tauri's NSIS and run on a scratch folder, then the launcher, staging, the icon, a quiet restart (`idle-seconds.txt` in the data folder holds it back until the check is ready, test hooks only), Restart to Update, the launcher's fallback and start-up through the launcher. The relaunch command is read back with `test_relaunch_command` (test hooks only). On 22 Oct 2026 it passed 8 of 8; the icon showed 5.4 s after staging, and the median start-up was 679 ms straight and 746 ms through the launcher. The real switch-over of the installed Sketch through its old update button is only tested by the user.
- **The relaunch strings are allocated with `CoTaskMemAlloc`** (`layout.rs`): the first build passed a buffer of its own, and Sketch crashed with heap corruption (0xC0000374) about 2 s after every start inside the install layout, which is the only place it sets them. Runs from `target\release` never showed it.

## Decisions for developer updates (23 Oct 2026)

After a push, the installed Sketch updates itself in the background, so the next start is the pushed version without opening Sketch and waiting for its own update. It's for development only, not a plan feature or a version of the app.

- **A `pre-push` hook, not `post-push` or a Claude hook.** Git has no post-push hook. `reference-transaction` would see the remote-tracking ref move after a push, but it runs on every ref change (each commit and checkout), three times per change. A Claude Code hook would only see pushes made from Claude. `pre-push` runs once per push from anything, so the script waits (up to 5 minutes) until `refs/remotes/origin/main` contains the pushed commit, which is when the push has landed; a failed push builds nothing. It only fires for `main` pushed to `origin`, which is what the in-app updater watches.
- **Hooks are opt-in per clone** (`core.hooksPath`, set by `npm run dev:hooks` to the repo's hooks folder, `.github/hooks` in the toolbox repo), since git never turns on a repo's hooks by itself. The folder is at the repo's root because `core.hooksPath` is one folder for the whole repo; the hook runs every `*/*/scripts/dev-update.mjs` once its own check has passed, so another tool can join by adding its own. `dev:hooks` refuses to replace a clone's own hooks path.
- **It reuses the in-app updater's build** instead of a second pipeline: the same data folder worktree (`build/sketch-update-build`, with its warm npm and Cargo caches), `build.lock`, `build.log`, `last-error.json` and `update-build.mjs` with the install folder, so the staging, `current.json` and clean-up are identical, and a running Sketch sees the staged version as its own (icon, quiet restart). When Sketch is already building the same commit it leaves it to that build; when it's building another, it waits for the lock to go and checks again. A commit that failed is skipped from the hook (as the app does) and retried by `npm run dev:update`.
- **The work runs in a process started through WMI**, hidden. That's what makes it work from a Claude session: the Claude app is packaged, and anything it starts has its AppData writes redirected into the package (CLAUDE.md trap), so a plain detached child would have staged into the package's copy. A WMI process also outlives the push and the terminal, and gets the user's normal environment, as a Sketch started from Explorer does.
- **Tested** on 23 Oct 2026 in a scratch install and bare clone: not installed, already current, a push that never lands, a push that lands mid-wait with Sketch building the same commit, a failed commit from the hook, waiting for another build's lock, the hook firing only for `main`, and a full background build staged into the scratch install. Then the real push of this change updated the installed Sketch.

## Decisions for the Full Performance Audit (F5)

- **Timed from the input's own timestamp to the start of the frame that shows the result**, in the release app through WebView2's debugging port (`scripts/perf.mjs`). It reuses `native-driver.mjs`, so it never touches the user's data, mouse speed or running Sketch. Timing in Node instead would have added the debugging connection's own delay to every number.
- **Budgets** (docs/performance-audit.md): one frame (17 ms) for anything that should feel instant, 50 ms for anything that opens, 100 ms for edits, 200 ms for whole-picture edits (the 4K paste goal from 6.7, also used for Fill and the Magic Wand), 0.5 s for copying and 1 s for saving, opening and starting. The 8K picture has four times the pixels, so its time budgets are four times the 4K ones, while frame rate and pointer lag budgets don't change with size.
- **Test photos are made, not stored**: smooth gradients with a little noise, so Fill spreads over large areas and saving and copying work as hard as on a real photo, without committing tens of MB of pictures.
- **Pasted pictures come as a PNG plus a bitmap**, as screenshot tools leave them. A bitmap alone (as Windows Forms puts one) makes WebView2 encode a PNG before Sketch sees it, which took 287 ms for a 4K photo against 117 ms; `check:speed` still pastes that way.
- **Fixes from the first audit** (23 Oct 2026):
  - *Drawing on big pictures*: frames ran at about 65 a second on 8K (every tool) because shrinking a canvas with high-quality smoothing rebuilds its downscaled copies every frame. The renderer now halves big canvases with plain smoothing first (`drawShrunk`), which is what those copies are, so the look is the same. 8K drawing went to the display's 240 frames a second.
  - *Fill and Magic Wand*: the flood search made two small arrays for every pixel it checked, several times per pixel. It now works the colour distance out in place and remembers each pixel's answer, the edge pass counts with running windows, and the wand's mask and outline are built in its worker. The results are byte for byte the same (checked on 4K and 8K photos). 4K fill went from 406 to about 160 ms and the wand from 518 to about 140; 8K from 1.7 and 2.3 s to about 0.6.
  - *Copy*: handing 33 MB of raw pixels to Rust took 0.3 s, and arboard's PNG encoding most of the rest. The page now sends a PNG made in its encoder worker, and `clip.rs` puts it on the clipboard as it is, with the CF_DIBV5 copy decoded from it. 4K copy went from 678 to about 380 ms, 8K from 2.7 to 1.4 s. Captures use the same writer with png's fast setting.
  - *Autosave on 8K*: building the `.sktch` zip (its checksum of the layer PNGs) kept the page busy for 106 ms. The zip is now made in the encoder worker, for autosave and Save alike.
  - *Image crates built for speed*: the release build stays `opt-level = "s"` for size, but the PNG and deflate crates are `opt-level = 3`, for 27 KB more.


## Decisions for Instant Open from the Capture Notification (F12)

- **The helper hands the capture over as the notification shows** (`hand_to_sketch` with `--open-capture=<file> --from-note --hidden=<id>`): over Sketch's pipe when a Sketch runs, otherwise by starting the launcher with it. A first launch with `--hidden` reads the file without deleting it (`read_shot`), opens it in its first window and keeps that window hidden; the page opens the capture, draws it, and then waits in `hidden_wait` with autosave held back (`holdAutosave`), update checks not started and leftover autosaves not reopened until it's shown. A running Sketch ignores `--hidden` unless it has a hidden window of its own waiting (then a newer capture replaces it, below), so with Sketch open captures still go to it on the click, as the plan said.
- **The click** sends `--open-capture=<file> --from-note --reveal=<id>` the same way. A Sketch whose hidden window waits for that id shows it (the page calls `show_window`, then `bring_to_front`, since the click passed the foreground on with `AllowSetForegroundWindow`) and deletes the file; anything else opens the capture as before. So the click works whatever state the hidden Sketch is in: not started yet, closed, or replaced. The notification going without a click sends `--drop-hidden=<id>`, which closes the hidden window, and Sketch with it when it was the only one.
- **One hidden window at most** (`Prepared` in `lib.rs`, a channel per window: true shows it, false closes it). A newer capture makes a new hidden window first and closes the old one after, so Sketch never finds itself with no windows and quits in between; the helper sends the new capture before it takes the old notification away (`note::close_older`), so the old one's `--drop-hidden` arrives after the replacement and is ignored. A hidden window closes by itself after 60 s in case the word that its notification went never arrives (it went while that Sketch was still starting and had no pipe yet).
- **Opened another way while hidden**: a plain start, a file or the paste key finds no shown window and opens a new one as usual; when the notification goes, only the hidden window closes.
- **3 seconds, timed by Sketch** (`note.rs`): Windows only offers 5 seconds (or the user's longer setting) or about 25, so each notification gets a 3-second timer that takes it off the screen (`ToastNotifier.Hide`, which needs the toast, so they're kept by id) and out of the notification centre (`History.RemoveGroupedTagWithId`), and drops its capture. This applies to every capture notification (the helper's, Sketch's own and a cold start's), so none are left in the notification centre any more; only the newest is kept, where before five were. `Dismissed` with any reason but `TimedOut` closes it too, as does `Failed`. `TimedOut` is left to the timer: a notification that skips its pop-up (Do Not Disturb, and checks' `SuppressPopup`) reports it at once, and the first build dropped every such capture. The helper also empties Sketch's part of the notification centre when it starts with the real data folder, since older versions left notifications there that did nothing when clicked (12 on this PC on 23 Oct 2026).
- **Speed**: the window shows 13 to 18 ms after the click and its first frame starts 19 to 24 ms after (release build, this PC), against about 355 ms for starting Sketch on the click. The hidden Sketch with its WebView2 processes holds about 236 MB of private memory (432 MB working set, much of it shared), more than the plan's 100 to 150 MB estimate, for its 3 seconds.
- **Checks** hold notifications for a minute with `note-ms.txt` in their data folder (test hooks only), so a slow step before a click doesn't lose one; the checks of the 3 seconds remove it. The helper's `WM_TEST_DISMISS` acts as a dismissal, since a check can't click the notification's X. Not checked automatically: the real click and dismissal, and whether Windows lets the shown window come to the front after a real click (only tested by hand).

## Decisions for Opening a Capture with Left Shift (F16)

- **One module, `shift_tap.rs`**, used by the helper's captures and Sketch's own (including a cold `--capture` start): `watch` runs a low-level keyboard hook for 1 second on a thread of its own with its own message loop (`MsgWaitForMultipleObjects`, which wakes for the hook's calls), rather than on the thread that shows the notification as the plan suggested: that thread is the capture's, which has no message loop. The hook passes every key on, its callback only updates the tap state and posts a message, and the capture opens after the hook is removed.
- **Sketch never watches in its own process.** Windows doesn't call a process's low-level hook for keys going to that process's own windows, and after Sketch's own capture a Sketch window is in front: the first build's hook in Sketch heard nothing there, though it did with another app in front. The page didn't get the tap either, since the WebView doesn't have the keyboard focus straight after the overlay closes. So Sketch starts `sketch-capture.exe --shift-tap=<id>` (`watch_elsewhere`) as soon as the capture is picked, before its windows come back, and that process hands `--shift-tap=<id>` to Sketch over its pipe on a tap; Sketch then clicks the notification, waiting up to a second for it if the tap came first (`note::click_soon`). The helper watches in its own process, right after its notification shows.
- **What counts** (`Taps`, unit tested): Left Shift down inside the second and up within 500 ms, with no other key going down meanwhile and no Ctrl, Alt, Windows key or Right Shift held as it goes down. Repeats while held don't count, and a Shift already down as the second starts is ignored until it's released. A press begun late in the second keeps the hook until its 500 ms are up.
- **The tap is the click** (`note::click(id)`): it takes the notification away and fires the same `Clicked` handler, so it reveals the hidden Sketch (F12), opens a quick capture (F9) and passes the foreground on exactly as the click does. With Sketch open the capture opens in a new window of it, as a click does.
- **The switch** is `shift_open` in `capture.json`, on by default and for files from before (`Settings::default`), shown in Settings > General as "Press Left Shift to open the capture" only while After a Capture shows a notification. No hook is installed when it's off or when captures open at once.
- **Speed**: with the hidden Sketch ready, the window shows 8 to 15 ms after the tap.
- **Checks** send keys with `SendInput` (`keys` in `native-driver.mjs`), which low-level hooks see as real keys and which go to whatever window is in front, so they only use keys that type nothing: Left and Right Shift, and F24 for "Shift with another key". Starting PowerShell takes a few hundred ms, so a tap meant for the second goes in the same call as the overlay drag (`overlay.dragThenKeys`, 400 ms after it closes, about when the notification has slid in). The helper's `WM_TEST_WATCHING` (test hooks only) says how many hooks it has installed, and for Sketch's own captures the check looks for a `--shift-tap` process left running, to prove nothing listens after its second. Not checked: a window running as administrator in front (Windows doesn't pass its keys to a normal app's hook, so the tap does nothing there and the notification still works), and whether a real tap brings Sketch to the front as well as the sent one.

## Decisions for the version number (23 Oct 2026)

- **The number counts itself up.** It's `package.json`'s major and minor, then the number of commits that changed `sketch/` (`git rev-list --count HEAD -- .`, in `build-info.mjs` as `__SKETCH_BUILD__.version`), so 0.1.30 at the time. Every update is a new commit, so every update gets a higher number with nothing to bump by hand. Bump the minor in `package.json` (and `tauri.conf.json`, `Cargo.toml`) for a big change if wanted; the last part keeps counting. A build outside git shows `.0`.
- **One spot for the version and the update icon**: the status bar's `st-version`, left of the picture size, shows `v0.1.30`, with the update icon (F11, unchanged: no tooltip, no click) in front of it while a version waits for a restart. Only the number has a tooltip ("Sketch version").
- **A spinner while a newer version builds** (`st-building`, Lucide's `LoaderCircle` turning once a second, three seconds with reduced motion; `aria-label="Update building"`, no tooltip or click, like the icon). It shows while `update.building` is set and the ready icon takes its place once the version is staged. It has its own class, not `st-update`, so `check:update`'s "no icon while building" test still means the ready icon.
- **Builds tell Sketch when they start and finish**, rather than Sketch checking more often. A build started by a push (`dev-update.mjs`) writes the same `build.lock`, but a Sketch only saw it at its next check (every 5 minutes), and a warm build takes about a minute and a half, so the spinner mostly never showed. Now `dev-update.mjs` (once its build has started) and `update-build.mjs` (in `finally`, so for in-app builds too, and after a failure) call `scripts/ping-sketch.mjs`, which writes `--update-check` to the pipe a second launch uses (`instance.rs`; the name is `key_hash` of the data folder, which the script recomputes). Sketch emits `update-check` to every window, and each runs its check. With no Sketch open there's no pipe and nothing happens; Sketch is never started. The timed checks stay as a fallback: every 5 minutes, and every 10 s while a build runs, in case a message is missed. A Sketch opened mid-build shows the spinner from its first check, 4 s after start.
- **Checks**: `check:update` holds the real build back (`last-error.json`) while it writes a stand-in `build.lock` (a commit git doesn't know counts as newer), pings, and expects the spinner within 2 s, then removes the lock, pings, and expects it gone within 2 s.
- **Settings ends with an About block**: no heading, a line above it, the app icon (`src-tauri/icons/128x128.png` at 40 px), "Sketch" and "Version 0.1.30". The About Sketch dialog shows the version above its build line too.

## Decisions for drawing round a capture (24 Oct 2026)

The user wanted the Snipping Tool's open edges: draw arrows, writing and circles past a capture without them being cut off, and have a copy hold the capture plus everything drawn round it.

- **Only captures** (`openCapture`, so every way a capture opens), not every picture: an ordinary picture keeps Paint's fixed canvas, since saving a photo shouldn't change its size because a stroke ran off it. `.sktch` files keep it (`edges` in `document.json`, no version bump: an older Sketch opens the whole grown canvas as the picture, which loses nothing).
- **The whiteboard's growth, with the capture framed in it.** `PaintDocument.edges` holds how far the canvas reaches past the capture on each side; `frameOf` turns it into the capture's rect and `isOpen` covers whiteboards and captures. Pixel tools grow the canvas at pointer-down exactly as on a board (`growBoardForPointer`, joined to the stroke's undo step), with a margin of one tile (`CAPTURE_MARGIN`) instead of the board's 1024 px: a 4K capture's first stroke otherwise grew its canvas to 6400 × 4720, and finding what's drawn outside took 108 ms on each copy (46 ms with the small margin). Growth is see-through: a capture's `fill` is null, which also skips `fillFor`'s 200 ms read of a 4K capture. Shapes, text and mark-up aren't clipped, as on a board.
- **Edges follow every whole-picture change.** `DocState` carries them, so undo and redo restore them. A growth adds to them (`grownEdges`), Rotate and Flip turn them (`turnEdges`, `flipEdges`), and anything else that changes the canvas (Crop, Crop to Selection, Trim to Content, Canvas Size, Resize) makes the new canvas all capture. Resize and Canvas Size first shrink a grown capture to what a copy holds (`settleEdges`, recorded with the change, put back if the dialog is cancelled), so the dialogs show that size.
- **What a copy holds** (`pictureArea`): the capture, every visible object's ink bounds and the painted pixels past its edges, found by reading only the four strips round the capture. No margin and no background: see-through past the capture, as Sketch's copies already keep transparency; JPEG and BMP get white. With nothing outside it's the capture exactly, so plain captures copy and save as before.
- **On screen**: the shadow and checkerboard sit behind the capture only, and what's drawn round it shows on the workspace grey. No size handles (the canvas size isn't the picture's); the crop box starts on the capture. The status bar shows the capture's size and positions from its top-left. Fill refuses an area reaching the canvas edge on a side the capture has grown past, as on a board.
- **Pastes and drops** on a capture land like a whiteboard's (the middle of the view, or the drop point), growing the canvas to hold them, rather than growing the picture.

## Fixes to opening a capture with Left Shift (24 Oct 2026)

The user reported a quick tap after a capture that opened nothing, and a capture opened by the tap (with Sketch open but minimised) that stayed behind the window being captured.

- **The tap was listened for too late.** The helper started its watch after putting the capture on the clipboard, writing its file and showing the notification, a few hundred ms on a big capture, and a cold `--capture` start after the notification too. A tap before that went unheard, and a Shift pressed before the hook and released after counted as held. Both now start the watch as soon as the capture is picked, and a tap that beats the notification waits for it (`note::click_soon`), as Sketch's own captures already did.
- **Windows opened for a launch never asked for the front.** Only a revealed hidden window (F12) called `bring_to_front`. A notification click hands the foreground on, so `show` alone brought other windows forward; after a Left Shift tap no process has that right (a low-level hook doesn't count as input), so a capture opened in a new window of a running Sketch, or in a Sketch the tap started, showed behind. `appReady` now calls `bring_to_front` (tao's `set_focus`, which presses Alt to get the right when it must) for every window opened for a file, paste or capture, but not for restarts or reopened autosaves.

## Decisions for Tabs for Several Pictures (F14)

- **The app object reads the tab showing.** Each open picture is a `Tab` in `src/app/store.ts` (document, undo history, view, file, `docIsNew`, `quickCapture`, `flattenOk`, Save As quality, crop box, last stroke end, autosave slot), in `tabs.list` with `tabs.active`. `app.doc`, `app.history`, `app.viewport` and the rest of those are getters and setters onto the current tab, so the rest of the code (tools, renderer, commands) stayed as it was. Things that belong to a moment rather than a picture (text being typed, a selection, picked shapes, a draft, guides, a marquee) stay on `app`, and switching tabs settles them first: text is committed, a selection placed, picks dropped (`leave` in `src/app/tabs.ts`).
- **Only the tab showing is drawn.** Switching swaps which tab `app` reads, gives that tab's view the canvas's size (read from the canvas, since a hidden page reports zero and a tab that wasn't showing missed any resize), keeps its picture centred if the window changed size meanwhile, and asks for a frame. Nothing is copied, so switching costs one frame's drawing.
- **New, New Whiteboard, Open, a drop beside the picture, launches and captures open a new tab** after the one showing (`actions.intoNewTab`), unless the tab showing is an untouched New picture, which is used instead. So New on an untouched picture does nothing, and Open no longer asks about the current picture's changes. This follows Windows 11 Paint's tabs. The plan said files from a second launch, a capture or a file go into a new tab; New and Open follow the same rule so the window never throws a picture away to show another.
- **Explorer's setting.** `openIn` keeps its stored values: `'window'` (the default) now means a new tab and `'here'` means in place of the picture showing, after asking. Settings calls them "A new tab" and "The tab showing". Rust's `deliver` is unchanged: it still sends the launch to the window used last, and that window opens it in a tab.
- **Ctrl+F4 closes a tab, not Ctrl+W.** The plan said Ctrl+W, but Ctrl+W is Resize, as in Paint, and keys can be changed in Settings. Ctrl+F4 is Windows' key for closing a document inside a window. Ctrl+Tab and Ctrl+Shift+Tab switch, with Ctrl+PageDown and Ctrl+PageUp as browsers have. Closing the last tab closes the window, through the window's own close so it asks in the same place. Closing a window asks about each tab with unsaved changes in turn, showing each (`confirmCloseAll`); a capture opened from its notification never asks (F9).
- **Autosave is per tab** (`src/app/recovery.ts`): each tab has its own slot, timer and last written revision. Each slot's `.json` also holds `group` (an id the window makes when it opens), `order` and `active`, so after a crash or a restart each window's tabs come back together, in order, with the one that was showing (`groupSlots`, `restoreTabs` in `launch.ts`). Slots from before F14 have no group and come back as a window each, as before. Opening, closing, moving or switching tabs rewrites only each slot's `.json` half a second later (`placesChanged`, Rust's `recovery_meta`, which never brings back a deleted slot), so the pictures aren't encoded again; the first full autosave rewrote every slot and the check after a kill caught the tab showing coming back wrong. A restart into a new version saves every tab first (`flushAll`). A slot reopened from another window is rewritten as this window's.
- **Restarts** report the tab showing's slot to `update_window_saved`, so Rust places the window by it as before; the other tabs' slots rank after every window's first and join their window by group. Launch `recover` carries a comma-separated list of slot ids for a window's tabs. A window with several tabs shows later than before, so a minimised second window could show first, leave no window in front, and the main window then kept the focus it took (3 of 4 `check:update` runs). `show_window` now remembers the window that had the focus at the restart's first show (`FOCUS_BEFORE` in `place.rs`) and gives it back after every window.
- **Tearing a tab off** writes its slot (even a blank one), stops this window writing it, and opens a window with `recover` set to it, which reopens it as after a restart. The undo history can't cross to another window's page, so it stays behind; the new window is placed like any new window, not at the pointer.
- **The tab strip** (`src/ui/TabStrip.tsx`) shows only with two or more tabs (the app grid gets a row for it, `.app.tabbed`). Tabs are 72 to 200 px wide and shrink to fit; the tab showing joins the options bar below. A press shows the tab; past 5 px it drags, moving past a neighbour's middle swaps them; let go more than 24 px outside the window to tear it off (the tab fades while it's out). Middle-click closes. A whiteboard with no file is named Whiteboard on its tab.
- **Carrying onto another tab** (F14.3, `src/app/tabDrag.ts`): a selection's move drag and picked shapes' move drag say what they carry (`ToolDrag.carry`) and can put back what they've moved (`cancel`). While one runs, the canvas controller looks under the pointer for a tab (`elementFromPoint`, since the canvas holds the pointer capture and the tab gets no hover), marks it, and after 500 ms resting there undoes the drag, takes the shapes or pixels out of the source as one step ("Move rectangle to …", or the selection cut as "Move selection to …"; a paste not yet placed just goes), switches tab, and hands the controller a new drag that keeps them under the pointer. Shapes get new ids on the target's object layer for new shapes (or a new Shapes layer) and are recorded as one step when the pointer is let go ("Move rectangle from …"); pixels become a floating pasted selection, placed with Enter or a click as usual (recorded as Paste). On a whiteboard or capture the canvas grows to hold the pixels first. Snapping is off while carried shapes follow the pointer.
- **Memory**: each tab's undo history has the usual 1 GB cap of its own; with many big pictures open the total can be several times that. Not capped across tabs yet.
- **Checks**: `check:native` has a Tabs part (switching keys and clicks with separate undo, carrying a rectangle onto another tab, ten tabs switching (0.4 ms of work a frame, worst 1.7 ms, on 24 Oct 2026), every tab back after a kill, tearing a tab off, closing tabs), and the checks that counted new windows for launches and captures now count tabs. `check:update`'s restart opens a file from Explorer as a second tab and a second window with `open_window`, and checks each window's tabs come back in one group. `npm run perf`'s `newPicture` closes the other tabs, so timings don't carry their memory.

## Decisions for Ctrl+X copy and close on a capture (24 Oct 2026)

The user asked for one key to finish marking up a capture: copy it and close it, instead of Ctrl+C then the window's close button.

- **Ctrl+X, through Cut.** With nothing selected and no shapes picked, Cut was disabled, so Ctrl+X did nothing there; with a selection or picked shapes it cuts as before. In the text editor's box Ctrl+X still cuts text, since `installShortcuts` skips keys aimed at text boxes. One command keeps the key's binding in Settings in one place; its palette keywords add "copy close capture".
- **Which pictures.** Any screen capture (`doc.edges` set), quick or not. A quick capture (F9) closes without asking; any other asks about unsaved changes as closing always does, since a copy isn't a save. Whiteboards and ordinary pictures keep Cut disabled with nothing selected.
- **What it copies and closes.** The same copy as Ctrl+Shift+C (`copy(true)`: every layer, shapes, text and what's drawn round the capture). Only when the copy works does it close, and it closes the capture's tab, not the window: captures open as tabs of the window used last (F14), so other pictures there stay. The last tab closes the window, as Ctrl+F4 does.
- **Check.** `check:native` marks up a quick capture, presses Ctrl+X, and checks the clipboard holds the capture, its tab closed with no dialog and the window stayed open.

## Decisions for Remove Background (F13)

- **The model is U²-Net** (Apache 2.0, the ONNX copy rembg publishes), picked by the user on 25 Oct 2026 from a comparison on photos, a screenshot and a drawing, timed on a 32-thread desktop through ONNX Runtime 1.31 on the processor:

  | Model | 1080p | 4K | Load | Add-on |
  |---|---|---|---|---|
  | U²-Netp | 0.10 s | 0.26 s | 0.07 s | 22 MB |
  | U²-Net | 0.15 s | 0.32 s | 0.3 s | 193 MB |
  | BiRefNet Lite (half precision) | 3.6 s | 4.0 s | 3.4 s | 132 MB |

  U²-Netp left ghosts of the backdrop on photos; BiRefNet had the cleanest edges and kept every object in front (U²-Net keeps only the main one, so a car photo lost the person beside it) but missed the 2-second budget. RMBG was left out: both versions are for non-commercial use only, and Sketch is MIT. No model handles flat drawings well.
- **An add-on, not in the installer.** ONNX Runtime (`onnxruntime.dll`, 17 MB) and the model (176 MB) download on first use into the data folder's `cutout` folder, from the `sketch-cutout-1` release of the toolbox repo (a tag with no `-v`, so the release workflow leaves it alone). `ort` is built with `load-dynamic`, so Sketch loads the runtime from there at run time and nothing of it is in the exe. Each file is checked by its size and SHA-256 (pinned in `cutout.rs`) before it's kept; a `.part` file is written first, so a cancelled or broken download never looks finished. A new model or runtime needs a new release tag and new hashes.
- **The page shrinks, Rust only runs the model.** The page draws the area at 320 × 320 (the model's size) and sends those raw pixels (400 KB); the mask comes back at 320 × 320 and the page scales it up with smoothing on the GPU, which also softens the edge. Picture-sized pixels never cross to Rust (the CLAUDE.md trap).
- **The model loads for each use** (0.3 s) and is dropped after, so it holds no memory between uses (U²-Net takes about 200 MB while loaded). A 1080p cut-out still takes well under the plan's 2 seconds end to end.
- **Where the cut-out goes.** On a layer, a copy goes on a new layer straight above it (`<name> cut out`, same opacity) and the original is hidden, as one step ("Remove background"), so the result shows and the original is never lost. With a selection, only the picked pixels are cut out: the model sees the selection's box, and pixels outside the outline stay. A lifted or pasted selection is cut out before it's placed, as the Adjust menu changes one. Locked and hidden layers refuse, as for adjustments.
- **Where it lives.** Remove Background is in the Adjust menu and the command palette, and is a button on the options bar of the three select tools, since that's where a selection is being made. Its first use opens a box offering the download, with its size, then shows the download's progress, with Cancel; a failed download says why and offers Try Again. In a plain browser it says it works only in the app.
- **Checks**: `check:native` serves the add-on from its own test server (`SKETCH_CUTOUT_URL`, files from `SKETCH_TEST_CUTOUT_FILES` or the installed Sketch's copy), so the download and its checks run as they would from GitHub. It cuts out an orange ball on a sky-to-grass backdrop at 1080p (corner see-through, middle solid, original hidden), undoes it, and times a second cut-out with no box.

## Decisions for removing the data folder on uninstall (25 Oct 2026)

- **Removed by default, kept on purpose.** The user's call: uninstalling removes everything Sketch keeps on the PC, the whole data folder (`%LOCALAPPDATA%\app.sketch.desktop`: settings, autosaves, waiting captures, update builds, the 193 MB Remove Background add-on, WebView2's profile), and anyone who wants to keep it says so. Autosaves can hold pictures never saved, so the wording names them.
- **Tauri's own box, turned round.** Tauri 2.12's uninstaller already has an unticked "Delete the application data" box on its confirm page, which removes `$LOCALAPPDATA\<identifier>` and `$APPDATA\<identifier>`. Its state can't be preset (the box is made in Tauri's own page callback, which hooks can't reach), so instead `tauri.conf.json`'s `customLanguageFiles` swaps in `src-tauri/windows/English.nsh`, a copy of Tauri's English strings with that one relabelled **Keep my settings, autosaves and Remove Background add-on**. Unticked, the default, now means remove. `NSIS_HOOK_PREUNINSTALL` reads the box into `$SketchKeepData` and zeroes Tauri's variable, so Tauri's own removal never runs, and `NSIS_HOOK_POSTUNINSTALL` removes the folders itself (`SKETCH_REMOVE_DATA`). The confirm page's text above the folder says what goes and to tick the box to keep it (`MUI_UNCONFIRMPAGE_TEXT_TOP`, set at run time in `un.SketchGuiInit`). A newer Tauri that adds a string to its language file fails the build (`!pragma warning error 6040` in `hooks.nsh`) rather than showing blank text: copy the new string into `English.nsh`. A full custom NSIS template was the other way and was turned down: it would fork Tauri's whole installer.
- **When it's kept.** The box, `/KEEPDATA` on the command line (how a silent uninstall keeps it; `install.py --remove --keep-data` passes it), an update (`/UPDATE`), and an uninstaller run in place. A normal uninstall (Settings > Apps, or `uninstall.exe /S`) copies itself to the temp folder and runs from there, while Tauri's installer, when it removes an installed Sketch before installing ("Uninstall before installing", the default when a different version is installed), runs it in place with `_?=`, so `$EXEDIR == $INSTDIR` means Sketch is being installed again; the confirm page says the data stays. Without this, upgrading by double-clicking a newer installer would have wiped autosaves. Silent installs (`install.py`) never show that page and never run the old uninstaller, and silent updates (F6) never run the installer at all.
- **The update build's worktree** (`build\sketch-update-build`) is registered in the clone Sketch was built from. Before removing the folder the uninstaller asks git for that clone's common git folder (`rev-parse --path-format=absolute --git-common-dir`) and runs `git worktree prune` there afterwards, through `nsExec` so no console shows. Without git, the clone keeps a stale entry, which `git worktree prune` (or git's own clean-up after three months) clears.
- **Files in use.** The uninstall already closes the capture helpers and every Sketch running from a version folder before it removes anything, but WebView2's processes let go of the profile a moment after Sketch closes, so the removal tries again every quarter-second for up to 5 seconds, then leaves what's still held and says so (`DetailPrint`; `install.py` prints it).
- **Only the default folder.** The uninstaller never removes a folder set with `SKETCH_DATA_DIR` or `--data-dir`: those are for checks and development, and could point anywhere.
- **Older uninstallers.** Silent updates never replace `uninstall.exe`, so a Sketch first installed before 1.2.0 keeps an uninstaller that always keeps the folder. `install.py --remove` removes the folder itself after the uninstaller, the same way (prune included), unless `--keep-data`; rerunning `python install.py` writes the new uninstaller.
- **Checks**: `check:uninstall` compiles a stand-in uninstaller from `SKETCH_KEEP_DATA_CHOICE` and `NSIS_HOOK_POSTUNINSTALL` (pointed at a scratch folder with `SKETCH_TEST_DATA_DIR`; it never runs the rest of the uninstall, which would close the real helpers and change the registry) and runs it the ways the real one runs: a normal `/S` uninstall removes the folder and prunes a real worktree of a scratch clone; the box, `/KEEPDATA`, `/UPDATE` and an in-place run keep it; a file held for 1.5 s is waited for; one held for good is left and the uninstall still finishes in under 10 seconds. The confirm page's two wordings were checked by eye on a stand-in uninstaller built from Tauri's page code.

## Decisions for Choose Your Pointer (F17)

The default stays Windows' normal arrow; anyone who wants a drawing pointer back picks one in Settings > General.

- **Four choices**: Normal arrow (the default), Small dot, Thin crosshair and Brush size circle, in a **Pointer over the picture** select with a preview on a light and a dark patch beside it. Saved as one `pointer` object (`shape`, `eraserOwn`, `eraserShape`, `dotSize`, `crossSize`, `color`) by `src/app/pointer.ts` and shared by every window through the `storage` event, like the theme. `sanitizePointer` (in `pointerStyle.ts`, which has no page code so tests can import it) turns anything missing or wrong into the default, so an install from before the setting (nothing saved under `sketch.pointer`) and a damaged value both keep the arrow, and nothing is written until someone changes the setting.
- **The arrow changes nothing at all.** With the arrow picked, the pointer code returns the cursor the app already used (the arrow, the text tool's I-beam), so nobody who leaves the setting alone sees any difference. With another choice the text tool's I-beam gives way to it, since the plan lists Text among the drawing tools.
- **Which tools**: the plan's brush, pencil, eraser, fill, shapes, lines and text, plus the mark-up tools (highlighter, blur, pixelate, numbered marker, callout, spotlight), which showed the crosshair before 24 Oct 2026 and are drawing tools too (`POINTER_TOOLS`). Select, Crop and Colour Picker keep their own pointers, as do pan (Space or middle button), the handles' resize arrows, move and grab, and the Alt+click pipette. Those still take priority over the chosen pointer.
- **Where it shows**: over the picture, not the grey workspace round it (the plan: "the normal arrow everywhere else"). A whiteboard and a capture have no edge to draw inside (pixel tools grow them), so there it shows over the whole canvas. The toolbars, options bar, menus and status bar never changed their cursor, and leaving the canvas hides the circle. While a drag draws a shape, callout or box the drag's own arrow or I-beam is swapped for the chosen pointer too (`dragCursor` in `input.ts`).
- **Dot and crosshair are CSS cursors** (`pointerCursor`): a small SVG data address with the hotspot on its middle pixel, so the system draws them and they move with the pointer with no lag. The picture is 4 px larger than the shape for its edge. The dot's width is 2 to 32 px (default 6), the crosshair's length 7 to 65 px (default 15, made odd so its lines sit on one middle pixel), each its own size setting; Windows and WebView2 cap cursor pictures at 128 px. A size control shows only for a shape in use.
- **Colour**: Automatic is a light pointer with a dark edge. The plan asked for a colour that "flips between dark and light"; a CSS cursor can't change with what's under it without reading the picture back from the GPU on every move, which would slow drawing and push the canvas onto the CPU, so the automatic pointer carries both tones and shows on any picture instead. The other choice is a colour from the colour box, with an edge of the opposite lightness. Dot and crosshair share the colour; the circle doesn't use it.
- **The circle** is a `div` (`.pointer-ring`) over the canvas with `pointer-events: none`, a dark ring with a light one inside, moved with a `transform`; the system pointer is `cursor: none` over the picture meanwhile. Its width is the brush size times the zoom (`ringWidth`), never under 6 px so a 1 px pencil can still be found. It is only for the brush, pencil and eraser, the tools whose size is a brush's. A tool with no such size (fill, shapes, text and the rest) shows a small dot where the circle was picked, rather than the arrow, so the click point is still marked; the dot size row is therefore shown for the circle too. `CanvasController` subscribes to `uiSignal`, so a brush size change (`[`, `]`, the options bar), a zoom, a tool change or a Settings change redraws it at once with the mouse still, and it follows the pointer through a stroke. Alt + right-drag still shows its own size circle while changing the size, and the pointer circle hides meanwhile.
- **The eraser's own pointer** is a switch (off by default) and, when on, a second choice (new default the circle) beside it. It shares the dot and crosshair size and colour with the other tools.
- **Checks**: `tests/pointer.test.ts` (old installs and damaged values read as the arrow, which tool shows which shape, the cursor pictures, the circle's width) and eight `check:native` checks that drive the real window with real mouse events over the debugging port and read the cursor the page computes: a fresh install and an install with earlier settings but no pointer both show the arrow with every drawing tool; Settings holds the choice; each choice with each drawing tool, and Select, Crop and the picker unchanged; the arrow over the tool rail, options bar, menu bar, status bar and beside the picture; the circle's width at 50%, 100% and 400% for brush, pencil and eraser, following a size change, a zoom and a stroke; the eraser's own pointer; and the choice, size and colour surviving a restart. The actual pixels of a cursor can't be read from the page, so what the dot and crosshair look like was checked as pictures, not on screen by the check.

## Decisions for Clean Up Rough Shapes (F18)

Draw a rough line, arrow, box or circle with the Brush or Pencil and hold still, with the button down, and it turns into a clean shape object. Settings > General has a **Clean up rough shapes** switch, on by default.

- **The hold** is half a second (`HOLD_MS`) with the pointer within 4 screen pixels (`STILL_PX`) of where it last moved further than that. Every move beyond 4 px starts the half second again from the new place; a tremor of a pixel or two doesn't. A real mouse sends no events while it is still, so the wait is a `setTimeout` of its own, set from the last real move. `QuickShape` (`src/tools/quickshape.ts`) keeps one per stroke and holds its `Tab`: when the timer fires it does nothing if another picture is showing or its layer is gone, and if the tab changes before the button goes up, the picture the stroke is in keeps the stroke as drawn. The timer starts on the first move, so a click without a drag never converts. A stroke of more than 20,000 points is never matched.
- **Brush and Pencil only.** The Eraser is never cleaned up, with the setting on or off. All brush types count (round, marker, highlighter); the shape takes the stroke's colour, its width (the brush size) and its opacity (the opacity setting times the nib's own, so a highlighter line stays see-through). Shift+click straight lines count too: they start from the last stroke's end, and holding on one cleans it up.
- **What it becomes**: a line (no heads), an arrow (a line with the Arrow tool's head at the tip; if that tool is set to no head, a filled one), a rectangle or an ellipse. Solid, unfilled, not turned; a rectangle takes the Rectangle tool's corner radius like any other. **Boxes and ovals are always upright.** Shape objects can turn, but fitting a turned box or oval needs a minimum-area fit and makes the drag that resizes a held shape ambiguous, while a hand-drawn box is nearly always upright. A slightly turned one becomes the upright box round it; a clearly turned one doesn't fit and stays a stroke. A square or a circle comes out only with Shift.
- **The match** (`src/tools/recognize.ts`, pure maths on the stroke's points, so tests can import it) answers only on a clear fit and otherwise leaves the stroke alone:
  - First the points are thinned (a hand shakes a pixel or so at every sample, which would make a straight path look long), and a stroke under 24 screen pixels corner to corner is ignored.
  - **Line**: the path isn't more than 15% longer than the chord, and no point strays more than 8% of the chord from it.
  - **Rectangle or ellipse**: the ends are within 20% of the path length, the stroke goes at least 85% of a turn round the middle (an overshoot counts, a "C" doesn't), and the box's shorter side is at least 12% of its longer. Then the average and the worst distance to the box's outline and to the ellipse (`f / |grad f|`, as a share of the box's size) are compared; one must pass (ellipse: mean 5%, worst 14%; rectangle: mean 4.5%, worst 12%) and beat the other's mean by 15%, so something between a box and an oval stays a stroke.
  - **Arrow**: five corners (Douglas-Peucker at 3, 5 and 8% of the stroke's size), read either way round, so the shaft can come first or last: tail, tip, one barb, back to the tip, the other barb. The two visits to the tip are close compared with the barbs, the barbs are 10% to 70% of the shaft and within a factor of two of each other, lean back at 10° to 72° from the shaft, and sit on opposite sides of it.
  - Scribbles, letters (L V Z N M W E F A T, a check mark, a step, S, waves), arcs, bows, triangles, figure eights and a line drawn out and back stay strokes. The thresholds were tuned on seeded hand-like strokes (`tests/recognize.test.ts`): 60 shaky lines, arrows, boxes and circles each (wobble up to 3% of the shape's size, a pixel or so of shake, gaps and overshoots) match 95 to 100%, and 960 scribbles, random polylines, arcs, bows and waves give no false shape. Real hands will differ; the numbers are constants at the top of the file.
- **Matched on the main thread, not in the flood-fill worker.** The plan said to use "the existing worker". The match takes about 0.01 ms for a 150-point stroke and 0.65 ms for a 20,000-point one (measured in `tests/recognize.test.ts`), and it runs once per hold, never per move. A worker round trip (posting the points, a message back) costs more than that and adds a delay between the hold and the shape appearing; the flood worker also only exists for fills. So the match stays on the main thread. What the hold adds to ordinary strokes is a `clearTimeout`/`setTimeout` pair on each move of more than 4 px, and one `push` of the move's points.
- **The shape replaces the stroke at once**, before the button goes up. The stroke is finished (so its change can be undone) and taken straight off the layer, and the shape is shown as the draft the Shapes tool uses. The rough stroke's pixels are therefore never left in the layer under the shape.
- **While the button is still down**, moving the pointer resizes the shape: a line's or arrow's end (the tip) moves by what the pointer moves; a box or oval gets wider or taller on a side by as much as the pointer moves away from the middle on that side (nearer the middle makes it smaller), so a stroke that ends by its starting corner grows when pulled outwards. Shift, held when the shape appears or later, keeps a box square and an oval round (taking the bigger side), and turns a line or arrow in 15° steps. Letting go keeps the shape: it is added to the object layer above the current layer as the Shapes and Lines tools do (a new "Shapes" layer if there isn't one), and picked, so it can be moved, resized or restyled at once.
- **Undo**: the rough stroke is recorded as an ordinary step ("Brush stroke", joined to a whiteboard's growth as usual), and the clean-up ("Clean up rectangle") is one more step that takes its pixels off and adds the shape. One Ctrl+Z brings the stroke back exactly as drawn (compared pixel for pixel with a stroke drawn without stopping), a second removes it, and redo makes the shape again. Recording the clean-up alone, with the stroke in no step of its own, would leave pixels in the layer that no step accounts for.
- **The setting** is the saved `cleanUp` (`true` or `false`) in `src/app/cleanUp.ts`, shared by every window through the `storage` event. `sanitizeCleanUp` (in `cleanUpPref.ts`, which has no page code so tests can import it) reads anything but `false` as on, so a fresh install, an install updated from before the setting (nothing saved under `sketch.cleanUp`) and a damaged value all have it on, and nothing is written until someone changes it. **Turn Shape Clean-Up On/Off** in the command palette (group Tools, ticked while on) switches it like the Settings checkbox; like Snap to Shapes and Pixel Grid it shows no toast. There is no explanatory text under the Settings switch beyond its label, because the plan asks for a switch only.
- **Checks**: `tests/recognize.test.ts` (lines, arrows either way round, boxes and circles in either direction with gaps and overshoots, and the strokes that must stay strokes) and `tests/cleanup.test.ts` (the setting's default for fresh and updated installs and for junk); and twelve `check:native` checks with real mouse events: a fresh install has it on and saves nothing; a stroke let go at once stays a stroke; a held box becomes a rectangle in the stroke's colour and width, already so while the button is down, with no rough pixels left, one undo bringing the stroke back pixel for pixel, a second removing it, and redo; the rectangle can be picked and moved; a circle, a line, an arrow and the pencil; scribbles, a letter and the eraser stay strokes; moving on restarts the wait, a 2 px tremor doesn't, and dragging resizes (a line's end follows); Shift squares and rounds; the switch off in Settings changes nothing and is kept after a restart; the palette command switches it both ways; an updated install has it on and writes nothing; and a held box on a whiteboard.
